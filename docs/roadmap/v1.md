## How to read this document

V1 is an operational contract: a stranger can pay, use it for a year, lose a laptop, upgrade in
place, and get support without the operator touching SQLite. Each clause is a requirement with an
acceptance test.

- No dates, durations, or effort estimates are used. Sequencing is by dependency and risk
  retirement.
- Markers: ✅ verified in this tree; ◐ audit-reported, re-verify; ○ decision or hypothesis.
- A gate is open only when its evidence artifact is linked.
- Terms are defined in [alpha.md §Terms](./alpha.md#terms).
- The canonical Alpha → Beta → V1 gate mapping is in [beta.md §1.3](./beta.md#gate-crosswalk).

### Scope boundaries

- In scope: the operational contract and the architectural decisions that make it reachable.
- Out of scope: feature completeness. Unneeded features are non-goals ([§10](#10-v1-non-goals));
  measured bets go to [v2.md](./v2.md).
- Not a schedule.

### Change triggers

A measured failure of a fork assumption (memory, save latency, projection cost, account conversion,
support load), a security incident that invalidates the threat model, or a customer obligation
(SLA, procurement, data residency) that a single node cannot meet. Each has a reversal trigger in
[§2](#2-the-three-forks).

## 1. V1 definition and the Beta→V1 relationship

> **V1:** a stranger can pay, use it for a year, lose a laptop, upgrade in place, and get support
> without the operator touching SQLite.

Each clause requires different work:

| Clause | Requirement | Failure mode if skipped |
| --- | --- | --- |
| **can pay** | Durable money → entitlement path, server-side enforcement, refunds/tax/dunning, a licence that survives a restart | Paid access silently evaporates; accounting cannot reconcile |
| **use it for a year** | Capacity limits that hold, no data loss under normal use, schema upgrades that preserve documents, retention and backups | The workspace becomes unusable or the operator becomes the support queue |
| **lose a laptop** | Account recovery that does not depend on the lost device, device inventory and revoke, a restore path for the owner | The customer's data exists but is unreachable — indistinguishable from loss |
| **upgrade in place** | Migration runner, N−1 fixtures, tested restore, rollback to the previous image | Upgrades become one-way doors; the operator delays them until forced |
| **get support** | Observability, request IDs, a diagnostics bundle, a status page, a runbook, a way to answer "what happened to my workspace" | Every question becomes an SSH session and a guess |

### Beta exit is a subset of V1

Beta means strangers can use it for real work with known limits. V1 means the same product can be
paid for and operated. V1 inherits every Beta exit gate and adds the operational, identity, billing,
compliance, and quality layers on top. Nothing here relaxes a Beta gate. The canonical gate mapping
is in [beta.md §1.3](./beta.md#gate-crosswalk).

| Beta exit gate (see [`beta.md`](./beta.md)) | V1 adds |
| --- | --- |
| Attachments durable on `/data`, in backup/restore | Attachments in the data inventory, in the `.suite` round trip, and in the restore drill |
| Multi-tab safety, persistence request, quota handling | Device-independent recovery and an account path for the same workspace |
| Migration runner + N−1 fixtures | Upgrade-in-place procedure with rollback and a tested downgrade refusal |
| Billing durable or publicly "not open" | Billing live: test-mode E2E, Portal, dunning, tax, refunds, rotation with grace |
| Published limits + load evidence | Capacity limits enforced per plan, with usage metering and overage behaviour |
| Threat model, CORS default deny, non-root container | External pentest, SBOM/signing, audit trail, incident response |
| Crash reporting + error boundary | SLOs, error budgets, on-call runbook, status page, support workflow |
| Docs truth pass | Compliance set: privacy, terms, DPA, GDPR export/delete, retention |
| Operator can restore the drill | A second operator can run the release drill without asking the primary |

○ **Decision:** V1 does **not** require a feature-complete product. It requires that the product a
stranger *can* use is safe to pay for, safe to lose access to, and safe to upgrade. Feature gaps are
acceptable if they are named, documented on the known-limitations page, and do not create silent
data loss.

### 1.1 V1.0 and V1.x

The 37-row checklist is the union of two releases. Treating it as one monolith makes the target look
much larger than the smallest honest paid release.

| Release | Target | Required rows | Deliberately deferred |
| --- | --- | --- | --- |
| **V1.0** | Take money safely for one operator who knows the customer | V1-1 through V1-24; V1-27 through V1-37 | External pentest, formal SLO/on-call, full procurement/DPA review |
| **V1.x** | Compliance, availability, and procurement | V1-25, V1-26, the procurement portion of V1-32; region choice, SSO, audit export | — |

knows the operator. Both are recorded as V1.x so they cannot silently disappear.

## 2. The three forks

These three decisions shape almost every other item in this document. Each gets a decision, a
rationale, a **reversal trigger**, and the evidence that would justify reversing it. The reversal
trigger is the important part: it turns a preference into a measurement.

### 2.1 Hosted paid vs self-host-first → **hosted paid + self-host parity**

**Decision.** ○ V1 ships one product in two editions from one codebase:

- **Hosted, paid.** Accounts are mandatory. A paid workspace must be recoverable by a person who no
  longer has the laptop.
- **Self-hosted, free.** Capability links remain the default and an operator **can** run it with no
  accounts at all. Accounts are available, not required.
- **Standalone/local-first.** Never requires an account, ever. The standalone build is a first-class
  profile, not a degraded one (✅ `session/mode.ts` already encodes `standalone` vs `relay`, and
  `mode.test.ts` prevents relay calls leaking into a standalone bundle).

The editions differ in authentication defaults and entitlements, not in document architecture. That
is a configuration difference, not an architecture fork; it preserves the one-architecture rule in
V2 R1.

**Rationale.**

1. **Charging creates obligations that capability links cannot meet.** Recovery, device management,
   support ("which workspace is this?"), invoicing identity, tax, compliance, and deletion requests are all
   *account* problems. A capability link cannot be re-issued to a verified person, and the relay
   cannot distinguish two holders of the same link (✅ `security-model.md`: "the server cannot tell
   two holders apart").
2. **Parity is the lower-cost path.** The self-host edition is the same image with different
   environment and no licence (✅ one `Dockerfile`, one `compose.yaml`, `SUITE_HOSTED` gates hosted
   defaults). Forking the editions would double the test matrix and break the local-first guarantee.
3. **Anonymous stays the default for everyone who is not paying.** Adding accounts must not turn a
   local-first tool into a sign-up wall. The launcher, the standalone build, and the "just open a
   workspace" path keep working with no identity at all.

**What accounts are mandatory for, and what they are not:**

| Capability | Anonymous + capability link | Optional account | Paid (account required) |
| --- | --- | --- | --- |
| Open and edit a local workspace | ✅ | ✅ | ✅ |
| Recover after losing the device | ❌ (only if the owner key survives elsewhere) | ✅ passkey / OAuth / magic link | ✅ plus support-assisted recovery |
| Device inventory and revoke | ❌ | ✅ | ✅ |
| Billing identity, invoices, tax | ❌ | — | ✅ |
| Support with a scoped, auditable view | ❌ | limited | ✅ |
| Deletion / export request traceable to a person | ❌ | ✅ | ✅ |

**Reversal trigger.** Two consecutive cohorts where hosted support cost per paying workspace exceeds
the plan's gross margin *because of identity work*, **or** a measured preference for self-hosting
among the paying cohort (self-host licences/support contracts outnumber hosted subscriptions). In
that case the fallback is **self-host-first with paid support**, keeping accounts optional and
deferring hosted billing — not dropping accounts from the product.

**Evidence to collect.** Account conversion among active workspaces; share-link-only usage;
support tickets requiring identity; recovery attempts that fail for lack of an account; churn reason
codes.

### 2.2 Single-node vs multi-replica → **single-node V1, published limits, tested restore**

**Decision.** ○ V1 runs one relay process, one SQLite writer per store, one in-process projection
worker, and one Caddy. It ships with:

- a published capacity table (workspaces, document bytes, attachment bytes, rooms, concurrent
  peers, projection bytes),
- persistence moved off the event loop (worker thread) or made incremental,
- automated backups with off-host copies and a **restore drill that is performed, not documented**,
- a stated RPO/RTO that a single node can actually meet.

Multi-replica is a **v1.1 project**, not a V1 gate, unless a signed obligation demands availability
the single node cannot provide.

**Rationale.**

1. **The code assumes one instance in four independent places** (◐ audit, consistent with
   `operations.md` and `architecture.md`): the projection worker keeps one peer per projection room
   and relies on last-write-wins against its own previous rebuild; rate limits are fixed-window
   counters in process memory; the room map and presence are in-process; SQLite allows one writer.
   Pretending otherwise is not a configuration change, it is a rewrite of the sync path.
2. **A second replica without shared presence and leases makes correctness worse, not better.** Two
   relays would each hold their own `LoroDoc` per room, each persist full snapshots, and each rebuild
   projections — with no lease deciding who wins.
3. **Restore is the availability feature that matters first.** A single node with automated,
   verified, off-host backups and a rehearsed restore beats two nodes with no restore path.

**Reversal trigger.** Any of: a customer obligation (contractual SLA, procurement requirement,
residency requirement) that a single node cannot meet; measured demand that exceeds the published
capacity *after* the persistence and projection work in [§4](#4-concrete-engineering-decisions) and
[§6](#6-performance-and-scale); or an availability incident whose root cause is the single instance
rather than the save path.

**When that trigger fires,** the order is fixed: control-plane Postgres first (already required for
accounts), then Redis for presence and rate limits, then room leases (advisory locks), then a load
balancer with sticky routing. That is ladder T1→T3 in [§5](#5-data-planes-and-postgres) — each rung
has its own evidence requirement.

**Evidence to collect.** `/api/admin/status` room counts and database sizes over time; event-loop
lag percentiles during saves; peak concurrent rooms per workspace; restore drill timings; incident
log.

### 2.3 One document vs index + card documents → **one Loro document per workspace for V1**

**Decision.** ○ V1 stores one `LoroDoc` per workspace, exactly as today (✅
`docs/architecture.md`: one `LoroDoc`, one sync room, one IndexedDB entry). The index/card split is
**deferred to v2**, gated on benchmarks and real usage.

**Rationale.**

1. **The measured cost is acceptable.** ◐ The workspace benchmark puts 5,000 cards at ≈12 MB and a
   full export at ≈25 ms. A workspace of that size still loads, saves, and projects within the
   budgets in [`design-inspirations.md` §8](../design-inspirations.md#8-performance-strategy).
2. **The split is not a storage tweak in practice.** It changes sharing (per-card ACL), undo
   scoping, presence merging, cross-document operations (create/trash/purge become convergent
   sequences with no transaction), offline pinning, and the number of rooms a relay must manage. It
   is a semantic change wearing a storage change's clothes.
3. **The seam already exists.** `WorkspaceDocument`'s export/import and card-container resolution are
   isolated so that a future split is a storage change (✅ ADR-0021 decision 5; its status keeps the
   card-document rationale as future work). Building the split before the seam hurts is the speculative work the design
   doc itself warns against.
4. **Splitting early would multiply the V1 surface** — twice the persistence paths, twice the
   projection inputs, a new class of orphan documents, and a tombstone/GC problem — at exactly the
   moment V1 needs fewer moving parts.

**What V1 does instead of splitting:**

- **Enforce the limits that make one document safe:** document bytes per workspace, cards per
  workspace, attachment bytes, projection bytes. These already exist as knobs (✅ `limits.ts`,
  `operations.md` limits table); V1 must publish them and make the over-limit behaviour legible in
  the UI.
- **Publish the split trigger** so the decision is not relitigated from taste: the index is no longer
  small and hot (index update size or load time grows with total body content), or one card body
  dominates load time for clients that never open it, or a shared card's editing traffic reaches
  peers who never open it.
- **Treat the benchmark as authoritative.** If it regresses, schedule the split; do not reargue the
  decision from preference.

**Reversal trigger.** ◐ benchmark or production telemetry showing that opening a board loads
megabytes unrelated to it; index documents exceeding the alarm threshold; p95 body-open latency
missed at the published card count; or a product requirement for per-card ACL that projections
cannot satisfy.

**Evidence to collect.** `pnpm bench` output per release; per-workspace document size distribution
from `/api/admin/status`; p95 time-to-interactive on the largest real workspaces; share projection
build time as a function of workspace size.

## 4. Concrete engineering decisions

Each decision has a recommended shape and an acceptance test. Where the shape is a refactor, the
rule is the same throughout: **move code behind the existing facade first, change behaviour second.**

### D1 — `packages/licence`: one token format, one verifier

- **Shape.** A workspace package owning the payload type, `LICENCE_FORMAT_VERSION`, `signLicence`,
  `verifyLicence`, and the error taxonomy. Consumers: the relay (enforcement wrappers stay in the
  server), the canvas (the "your key expired" message), and billing (issuance).
- **Why.** ✅ `services/billing/issue.ts` imports `../../apps/collab-server/src/licence.ts`, which
  violates the package graph, drags app source into a Lambda bundle, and mixes two test runners. The
  canvas has its own parser, which is how client/server drift starts.
- **Acceptance.** A dependency-boundary test (same style as `mode.test.ts`) fails if `services/*`
  imports `apps/*` or if `packages/licence` imports either. One conformance suite signs in one
  consumer and verifies in the others; a property test round-trips arbitrary claims. `pnpm why
  @suite/licence` shows exactly three consumers.

### D2 — One migration runner, `busy_timeout`, N−1 fixtures, six stores

- **Shape.** A small shared helper: `PRAGMA user_version`, an ordered migration list per database,
  one transaction per migration, a boot log line naming the version and what ran, and a refusal to
  open a database whose `user_version` is newer than the binary. `busy_timeout` set on every
  connection at open.
- **Why.** ✅ Six stores (`documents`, `shares`, `workspaces`, `settings`, `licences`, `attachments`)
  each run their own `PRAGMA table_info` + `ALTER TABLE`. In the current compose file, five are
  configured; attachments defaults to the process working directory, and settings and licences
  default to `:memory:`. Upgrade correctness is distributed across six files, and a concurrent
  `sqlite3` invocation can fail instantly with `SQLITE_BUSY`.
- **Acceptance.** A fixture directory holds one file per store at N−1. A test opens each, migrates,
  asserts the expected rows survive, and re-runs to prove idempotence. A "newer than binary" fixture
  refuses to open with a clear error. A `PRAGMA busy_timeout` assertion runs against every opened
  connection.

### D3 — Persistence: worker thread, incremental updates, lag as the metric

- **Shape.** Move SQLite writes to a worker thread that owns the connection (preserving the
  single-writer invariant) **and** persist incremental Loro updates with periodic compaction. Both,
  not either: incremental writes cut amplification; the worker removes the stall.
- **Why.** ✅ `node:sqlite`'s `DatabaseSync` is synchronous and the relay upserts a full snapshot per
  dirty room on a timer, so every save blocks the WebSocket path. At the published document size the
  amplification is substantial, and saves serialize across rooms.
- **Acceptance.** A load test at the published room count and document size reports p99 event-loop
  lag under budget, a bounded WAL, and successful crash recovery from an interrupted save. The
  metric exported is lag, not save duration — save duration can look fine while the loop is stalled.

### D4 — Projection: skip, diff-apply, cap, then lease

- **Shape.** Skip when the source version vector is unchanged; apply the publish diff machinery
  instead of clear-and-rewrite; debounce per share; record build time per share and cap it; only if
  multi-replica ever happens, add a per-room lease (Postgres advisory lock) and remove the
  single-peer/LWW assumption.
- **Why.** ✅ The worker rebuilds every share of a workspace on every save, in one process, with one
  peer per room and LWW as the concurrency model. Cost is O(shares × workspace).
- **Acceptance.** A test proves the skip path (unchanged vector → no rebuild). A benchmark shows
  rebuild cost after diff-apply. Per-share build time appears in metrics. The architecture doc is
  updated to state the assumption the lease would remove.

### D5 — `packages/contracts`, `/api/v1`, stable error codes

- **Shape.** Zod request/response schemas per route; the client derives types instead of hand-writing
  `fetch`; routes under `/api/v1`; every failure returns
  `{ error: { code, message, requestId } }` where `code` is a stable enum and `message` is
  human-facing. The 64 KiB control-plane body cap becomes a documented contract with its own error
  code, not an implementation detail.
- **Why.** ✅ The client hand-writes calls, the server hand-parses bodies, errors are free strings,
  and routes are unversioned. ✅ `http.ts:156` caps bodies at 64 KiB.
- **Acceptance.** A route-table test asserts every registered route has a schema and a non-empty
  error-code set. Oversized body returns the documented code and envelope. The canvas compiles
  against inferred types with no hand-written response interfaces. A breaking change requires a new
  version prefix.

### D6 — CORS default deny

- **Shape.** No `SUITE_ALLOWED_ORIGINS` → no CORS headers at all (same-origin only). `*` only when
  explicitly configured. Docs, `.env.example`, and tests agree.
- **Why.** ✅ `config.ts:277` returns `["*"]` for an empty value while `.env.example` and
  `security-model.md` both describe a same-origin default.
- **Acceptance.** A test asserts the absence of `Access-Control-Allow-Origin` on a cross-origin
  request with no configuration. `*` appears only when set. The three documents above are edited in
  the same change.

### D7 — Container hardening and runtime shape

- **Shape.** Non-root user; read-only root filesystem with explicit writable mounts (`/data`,
  `/tmp` if needed); CPU/memory limits in compose; multi-stage build so dev dependencies do not ship;
  healthcheck wired to `/health`.
- **Why.** ✅ `Dockerfile` has no `USER`; the runtime currently runs as root.
- **Acceptance.** `docker inspect` shows a non-root `User`; the container starts with
  `read_only: true` and passes e2e; the image contains no dev dependency; compose declares limits
  and a healthcheck; a "runs as root" assertion in CI fails the build.

### D8 — Owner key: accounts move paid users to cookies; anonymous gets WebCrypto

- **Shape.** Paid/account users authenticate with `HttpOnly`, `Secure`, `SameSite` cookies — the
  owner key stops being a long-lived bearer in `localStorage` for them. Anonymous users keep a
  non-extractable WebCrypto key wrapper in IndexedDB (the raw key never becomes a JS string). The
  XSS tradeoff is stated in the security model: a non-extractable key raises the cost of exfiltration
  but does not stop an attacker who can drive the crypto in-page.
- **Why.** ✅ The owner key lives in `localStorage` today (`suite.ownerKey.<workspaceId>`), readable by
  any same-origin script. CSP lowers but does not remove that risk.
- **Acceptance.** An injected-script test cannot read the key material. Cookie flags are asserted in
  a test. `security-model.md` gains an "accepted risk" entry describing exactly what remains possible.

### D9 — Backpressure and per-room limits

- **Shape.** Cap per-message and per-room update bytes, rate-limit updates per room and per
  connection, and log + deny oversized payloads with a stable code. Test with a deliberately large
  paste.
- **Why.** ◐ HTTP JSON is capped and attachments are capped, but document updates have no total-size
  or rate cap; one client can force a large `applyUpdates` and a full-state save.
- **Acceptance.** Oversized update is refused without disconnecting silently; the refusal is counted
  in metrics and named in the logs; a client that floods is throttled, not dropped without
  explanation; the behaviour is in the known-limitations page.

### D10 — Admin scoping, MFA, per-action audit

- **Shape.** Split `SUITE_ADMIN_TOKEN` into at least read-only and mutate scopes; require a second
  factor for mutate; write an audit row per action (actor, action, target, result, request id); put
  the panel on a separate hostname with an IP allowlist option; document the blast radius of the
  current token (full data access, unscoped) until it is replaced.
- **Why.** ◐ `security-model.md` lists audit as absent and describes the token as unscoped.
- **Acceptance.** A read-only token cannot mutate (test). Every mutating route emits an audit row
  (test enumerates routes). MFA is enforced for mutate scope. The operations doc has an incident
  recipe for "admin token leaked".

### D11 — `WorkspaceSession` factory replacing module-load singletons

- **Shape.** Create the doc, `WorkspaceDocument`, presence stores, persistence, and provider in a
  session object at boot, injected through context; keep the module-level store only as a thin
  adapter during the migration. Use `isStandalone()` in the provider condition so the
  `import.meta.env.MODE` define can go.
- **Why.** ✅ `useCanvasStore.ts` builds all of it at module load and `SESSION` is read at import.
  Consequences: no workspace switch without a reload, tests must reset modules, a future account
  switch is harder than it should be, and the standalone profile needs a build-time hack.
- **Acceptance.** Two sessions can exist in one test process without cross-talk; workspace switching
  needs no reload; `mode.test.ts` still passes; the define is removed.

### D12 — God-object splits behind existing facades

- **Shape.** `WorkspaceDocument` (✅ 3,558 lines, 140 methods) into aggregate modules — cards, boards,
  types/tags, edges/sections, content — with the class keeping the public surface. `CanvasBoard`
  (✅ 2,412) into gesture hooks (marquee, drag, connect, section, viewport, keyboard). `adminHttp`
  (✅ 1,516) into route modules. `projectionWorker` (✅ 1,468) into phases (scope, redact, rebuild,
  publish).
- **Why.** Internal organisation is good; the cost is review, onboarding, merge conflicts, and the
  difficulty of testing one behaviour at a time.
- **Acceptance.** File-size ceiling enforced in CI for these four paths; public API unchanged (no
  test rewrites required); coverage of the moved code does not fall; one aggregate extracted per
  change, with behaviour verified by the existing suite before moving the next.

## 5. Data planes and Postgres

**Six SQLite stores is reasonable.** They are split by write pattern and risk, not by tenant:
documents carry high-frequency room saves, attachments carry large blobs, and settings/licences are
almost read-only. Physical isolation keeps a lock or corruption in one from taking down the others.
Settings and licences are the lowest-cost merge candidates if the file count ever becomes a real
burden; documents and attachments should stay separate. The operator burden is drills and
documentation, not the file count.

### 5.1 Two planes, two answers

| | **Document plane** | **Control plane** |
| --- | --- | --- |
| **Contents** | Loro snapshots, share projections, attachment bytes | users, sessions, workspaces, owner hashes, shares, licences, limits, usage, audit, jobs |
| **Today** | SQLite BLOBs, one row per room; attachments in their own SQLite file (✅ `persistence.ts`, `attachments.ts`) | six SQLite files, single process |
| **V1 target** | **Keep opaque bytes**; stay on SQLite for the single node | **Postgres**, arriving with Better Auth |
| **Reason** | A new engine does not make a 12 MB snapshot smaller, cheaper to apply, or less resident in memory | Identity, entitlements, quotas, audit and multi-replica coordination need rows, constraints, and shared visibility |

### 5.2 What Postgres fixes, and what it does not

| Fixes | Does not fix |
| --- | --- |
| Sessions verified by more than one relay | Event-loop-blocking saves — `pg` is also synchronous on the caller's path, plus a round trip |
| Queryable operations ("who is over quota", "which licences lapse") | Write amplification — the same whole-snapshot upsert, now over the network |
| Durable billing and idempotency with conditional writes | Room memory residency — every open room's `LoroDoc` is still in the heap |
| Audit trail for admin actions, revocations, rotations | Projection fan-out — O(shares × workspace) is not in the database |
| Advisory locks, `LISTEN/NOTIFY`, `FOR UPDATE SKIP LOCKED` for jobs | Presence — `EphemeralStore` is in-process; multi-replica needs pub/sub, not Postgres |
| Backups and PITR with a real toolchain | IndexedDB eviction, offline reload, multi-tab writes — all client-side |
| Retention and deletion expressible as SQL | Document queryability — a BLOB has no columns; search stays in-app |

○ **Rule:** Postgres is the answer to *"who are you, what may you open, and what did you use"*. It is
not the answer to *"why is this board slow"*.

### 5.3 Adapter promotion, not a second architecture

The seams already exist: `DocumentStore`, `DocumentInventory`, `DocumentMaintenance`, `ShareStore`,
`WorkspaceRegistry`, `SettingsStore`. Promotion means **a new implementation of the same interface**,
selected by configuration:

```
createDocumentStore(path) → SQLiteDocumentStore   (self-host, single node)
                          → PostgresDocumentStore (hosted, multi-replica, sharded)
                          → ObjectStoreDocuments  (large workspaces: object storage + metadata row)
```

- ○ **Acceptance for any promotion:** a conformance suite runs the *same assertions* against
  in-memory, SQLite, and the new implementation; promotion is a config value backed by that suite.
- ○ **Because documents are opaque bytes keyed by name**, migrating a workspace between substrates is
  a copy, not a schema mapping: no dual-write, no backfill.
- ○ **Add a blob format tag now** (`loro-snapshot-v1`) so a future substrate can refuse or convert
  unknown formats instead of importing garbage. This costs less before data exists than after.

### 5.4 Topology ladder (deployment tiers, not customer tiers)

| Tier | Topology | Solves | Entry condition |
| --- | --- | --- | --- |
| **T0** | One Node + Caddy + SQLite | Self-host, small hosted | Now |
| **T1** | Postgres control plane + relay + SQLite docs | Accounts, licences, audit, usage, multi-replica read paths | Better Auth arrives (V1) |
| **T2** | Worker process for saves/projections; docs in PG or object storage | Event-loop stalls, memory ceiling | T1 plus load evidence |
| **T3** | Redis (presence, rate limits) + room leases + sticky routing | Horizontal scale, HA | A signed availability obligation |
| **T4** | DB/schema per tenant + region pinning | Enterprise, residency | Procurement demand |

○ **The trap to name explicitly:** T1 on the same small box *tightens* memory. Adding Postgres feels
like progress and can make the single node slower. Plan the RAM before adding the engine, and do not
skip the persistence work in D3 by hoping the database absorbs it.

### 5.5 Sharing Better Auth's database

- ○ **One cluster, separate databases or schemas** (`auth`, `suite`, later `billing`), **separate
  roles**.
- ○ **The relay's role must not read `auth.session` or `auth.account`.** Verify sessions with a JWT
  via JWKS. Password hashes and OAuth tokens must not be reachable from the process that holds
  plaintext documents.
- ○ **PII segregation.** Better Auth stores email, IP, user agent. The document plane stores none
  today; keep it that way so a relay backup is not a credential or contact dump (◐ the security model
  already notes backups are unencrypted).
- ○ **Never put auth tables in the document SQLite file** — that file is copied, tarred, and restored
  by shell scripts.
- ○ **Cross-store deletion is a design constraint, not a cleanup script.** Put `user_id` on every
  tenant row (workspaces, shares, licences, usage, audit) *before* there is data, so "delete my
  account" is expressible as one ordered procedure across stores and backups.

### 5.6 What paid tiers actually sell

Quotas, guarantees, retention, region, priority, and support — **not a different engine**:

| Sold | Not sold |
| --- | --- |
| Larger document/attachment/workspace quotas (knobs already exist) | "Your data is in a real database" |
| Longer retention, more backup generations, faster restore target | A separate document architecture for large plans |
| Region selection (a second Postgres + relay) | A per-tier schema |
| Priority on heavy operations (a queue, not a fork) | A per-tier code path or test matrix |
| Audit export, SSO, admin roles (later) | — |
| Support and an SLA | — |

○ **Meter from the start:** document bytes, attachment bytes, active shares, projection time.
Pricing requires usage measurement, and usage rows belong in the control plane as soon as it exists.

## 6. Performance and scale

### 6.1 Budgets are already written down

The targets live in [`design-inspirations.md` §8](../design-inspirations.md#8-performance-strategy):
60 fps pan/zoom at ~200 visible cards with no long task over 50 ms; drag-to-paint under one frame;
zero persisted CRDT writes during a gesture; warm board open under 100 ms; card body open under
150 ms p95; index ≈1 KB per card with an alarm at 10 MB; card document p95 under 200 KB; presence
bounded per gesture. V1 does not relax these; it makes them enforceable (QU5).

### 6.2 The memory math that decides the instance size

◐ A 5,000-card workspace is ≈12 MB, and `SUITE_PROJECTION_ROOMS_MAX` defaults to 128 (provisional
until the load test). 128 × ~12 MB
≈ **1.5 GB on a 2 GB box** — before the Node heap, the WASM runtime, Caddy, and the OS. That number,
not disk, is the capacity limit of the current design. So room count and document size must be
published limits (S4); idle projection rooms must be evictable and lazy-openable (the sweep exists,
eviction is the work); and the load test must report memory per room at the published document size,
not requests per second.

### 6.3 The three stalls

| Stall | Cause | Fix | Proof |
| --- | --- | --- | --- |
| **Save stall** | Full-state synchronous upsert per dirty room on a timer | Worker-thread SQLite + incremental updates + compaction (D3) | p99 event-loop lag at load |
| **Projection stall** | Every save rebuilds every share, clear-and-rewrite, one peer/LWW | Skip by version vector, diff-apply, debounce, cap (D4) | rebuild count and build time per save |
| **Open stall** | Whole document loads for a board that shows a fraction of it | Lower-cost fixes now; document split only at the trigger | time-to-interactive at the largest real workspace |

### 6.4 Lower-cost fixes, in order

1. **Viewport culling** of card nodes and their editors — mount bodies only near the viewport.
2. **Lazy editors** — title plus preview until focused; mounting every editor dominates a large board.
3. **Incremental snapshots** — reuse unchanged collections and records (the snapshot store already
   does this; keep it true as surfaces are added).
4. **Batch and throttle** — presence bounded per gesture, CRDT writes on release, derived lists
   recomputed on structural change.
5. **Derived indexes** — section membership and view results from sorted geometry and predicate
   indexes, never a per-frame scan.
6. **No high-frequency CRDT** — carets and drags are ephemeral; a keystroke is not a structural write.

### 6.5 The split trigger (stated once, referenced everywhere)

○ Split the document when **the index is no longer small and hot**: index update size or load time
grows with total body content; opening a board loads megabytes unrelated to it; one shared card's
editing traffic reaches clients that never open it. Until then, splitting is speculative work that
costs atomicity, undo scoping, presence merging, and per-room auth complexity for a problem the
benchmark has not shown.

## 8. Release engineering and operations

### 8.1 Release

- Required checks on the default branch: `quality` (lint, typecheck, unit, contract, mutation
  incremental) and `e2e` (Chromium smoke). Red blocks merge.
- Semver tags from conventional commits; `CHANGELOG.md` generated per tag; release notes state
  migrations, breaking changes, and known limitations.
- Images built from a digest-pinned base, pushed by digest, signed, and accompanied by an SBOM.
- **Rollback is a first-class path:** the previous digest stays pullable, the migration runner
  refuses a binary older than the schema, and the documented rollback is "restore the snapshot, run
  the previous digest" — not "downgrade the schema in place".

### 8.2 Operations

- Backups: automated, verified, copied off-host, with the attachment store included (DR1) and a
  manifest that records size and hash per file.
- **Restore drill:** performed against a fresh data directory, timed, and recorded. The drill is the
  RTO evidence; a document describing a restore is not.
- SLOs: control-plane availability, share resolution, and save acknowledgement, each with an error
  budget and a burn-rate alert.
- On-call: the runbook's six recipes (O5), an escalation path, and a decision rule for "restore vs.
  wait"; incident communication via status page, template, and a customer notification path (C8).

### 14.2 Conflict notes (explicit, not silently resolved)

**Conflict 1 — the design doc's target is index + card documents; V1 is one document.**
`design-inspirations.md` §4.2 describes a target index document plus card documents, and §7 calls
card-level sharing a core requirement that depends on that split. §8 then decides to keep one
document for now. V1 resolves the tension in favour of §8's decision, for the reasons in
[§2.3](#23-one-document-vs-index--card-documents--one-loro-document-per-workspace-for-v1): the
measured cost is acceptable, the split is a semantic change, and the seam is preserved. **The target
is not rejected — it is sequenced.** V2 owns it, gated on the benchmark.

**Conflict 2 — the design doc treats card-level sharing as core; V1 ships board/card/selection
projections instead.** ADR-0021 deferred card-level sharing; ADR-0022 superseded it *for S1* and
shipped projection capabilities; ADR-0023 added selection shares. V1 takes the shipped projection
model as the sharing contract. The consequence is documented explicitly: a share is a
**projection**, not a per-card ACL, and a card share copies content into a synthetic `share-board`.
Card-level ACL remains future work.

**Conflict 3 — the audit's sequence was illustrative and time-bound; this document is not.**
The audit's ordering by risk is kept; its calendar framing is removed. The dependency table in
[§12](#12-dependency-ordered-sequence) is the replacement, and it changes one thing: contracts and
quality work (E) run in parallel with identity and billing (B) rather than at the end, because B and
C change the client/server boundary that E is supposed to stabilise.

**Conflict 4 — "Postgres for paid users" vs "Postgres for the control plane".** The framing that
paid users are "promoted" to a real database is explicitly rejected. Postgres arrives with Better
Auth, for the control plane, for every edition that runs accounts. Document bytes stay opaque. What
paid users get is quotas, retention, region, priority, and support ([§5.6](#56-what-paid-tiers-actually-sell)),
not a different engine.

**Conflict 5 — ADR-0019 vs the later typed-links proposal.** ADR-0019 stands. V2's typed-link bet
(if it lands) must supersede it with a new ADR and must land after views v2, because a type registry
only earns its cost once something queries the types. V1 does nothing here.
