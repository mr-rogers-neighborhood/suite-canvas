V2 is downstream of five artifacts. It may **extend** them, and in three places it **proposes to
supersede or contradict** them. Both are recorded here rather than discovered later.

| Artifact | What it fixes | How V2 relates |

| [design-inspirations.md](../design-inspirations.md) ✅ | Direction and purpose, vocabulary, budgets, one-document decision, non-goals, open questions | V2 inherits the direction and the non-goals verbatim. | [ADR-0019](../decisions/0019-references-not-typed-links.md) ✅ | References, not typed links; arrows are board-scoped; a property block is a view, never a store | **Bet B proposes to supersede the "no relation types" half** under the condition ADR-0019 itself set: a query layer exists. Bet B also **keeps** the references half and the view-never-store rule. |
| [ADR-0021](../decisions/0021-sharing-seam-deferred.md) → [ADR-0022](../decisions/0022-share-projection-links.md) ✅ | The sharing seam: capability tokens, live projection rooms, staged roles; ADR-0021 superseded for S1 by ADR-0022 | V2 treats projections as the sharing model of record. Card-level *documents* remain future work. |
| [ADR-0023](../decisions/0023-selection-projections.md) ✅ | Selection-scoped projections: part of a board shared without duplicating the workspace | V2 assumes selection projections exist and must be kept working by every new surface (themes, annotations, relations). |

### Conflict 1 — the design doc's eventual index/card split vs. V1's one-document decision

The design doc calls for an eventual **index document plus one document per card**
(◐ `design-inspirations.md` §4.2, §8 "When to split documents"). V1 keeps **one Loro
document per workspace** (○ shared convention, recorded in [v1.md](./v1.md)).

These are not in contradiction *if* the split is treated as a **storage change behind an interface**,
not a semantic rewrite:

- V1 ships one document, with the seam designed so a split is possible ✅ (`design-inspirations.md`
  §8 "Document boundaries in Loro": "keep production storage as one document for now… design the
  index/card seam so a split is a storage change, not a semantic rewrite").
- V2 (Bet F) **may** revisit the split, but only when a benchmark says the index no longer fits the
  "small, hot" profile. Until then, V2 bets are designed to be *split-compatible*: no bet may
  require cross-object atomicity that a split would break.
- Concretely: Bet D's annotations and Bet E's plans operate on workspace-level records that a split
  would keep in the index; neither may depend on reading a card body to answer a query.

### Conflict 2 — ADR-0019's "typed links only after a query layer" vs. V2's typed links

ADR-0019 ✅ says relation types can be added later "if a query layer arrives and typed links earn
their cost", and pre-authorizes exactly one mechanism: "a `relationTypeId` can be added to `edges`
as a field, with derived backlinks unchanged".

Bet B **is** that arrival: Views v2 (Bet A) is a query layer. So Bet B is not a reversal of
ADR-0019's reasoning — it is the trigger ADR-0019 named. It still requires a **new ADR** that
supersedes the "no relation types" decision while preserving the references half. No V2 work may
ship relation types before view predicates exist, or V2 reproduces the exact failure ADR-0019
rejected: "a type picker with nothing to show for it" ✅.

### Conflict 3 — card-level sharing deferred vs. projection shares already shipped

ADR-0020 ✅ defers **card-level sharing** ("it requires separate card rooms, a redacted index
projection and per-room auth"); ADR-0022/0023 ✅ already ship **projection** shares (board, card,
selection) as capability tokens over live projection rooms.

Both are true, and the distinction matters for V2:

- **Shipped today:** a *projection* of a subset into its own room (`share-<token>`), with explicit
  redaction ("Private card" stubs), manual publish back into the workspace, and field-granular
  conflict resolution ✅.
- **Still deferred:** a **card document** with its own ACL, loaded lazily, that is the unit of
  sharing in the index/card split. That is Bet F territory, not Bet D territory.
- V2 consequence: any bet that adds a new record type (relations, annotations, themes, sources) must
  define **what a projection does with it** — copy, redact, or drop — *before* it ships. A bet that
  cannot answer that question is not ready.

### What would change this document

- A gate in §2 failing (usage never arrives, load tests never run, support load stays zero) ⇒ V2 is
  mostly deleted, not deferred.
- Views v2 slipping ⇒ Bets B, C, D and E lose their query precondition and reorder.
- A measured ceiling hit in V1 (memory, save stalls, document size) ⇒ Bet F jumps the queue.
- Any bet requiring a second architecture ⇒ the bet is cut, per §1 R1.

## 1. Rules and non-negotiables

These are constraints, not preferences. Every bet in §3–§9 is evaluated against them, and a bet that
needs an exception is a bet that needs a new ADR first. Each rule is ○ (a decision) unless its
rationale cites a verified fact.

| # | Rule | Why it is non-negotiable | Consequence if violated |
| --- | --- | --- | --- |
| **R1** | **One architecture. No tier fork.** Hosted and self-hosted run the same code; paid buys quotas, guarantees, topology, and support — never a second engine or a feature-gated code path. | The editions table promises parity; a fork doubles the test matrix and drifts. ◐ audit: `services/billing/handler.ts` already importing app source is the early symptom of the wrong direction. | Cut the feature or redesign it to be limit-based. |
| **R2** | **Plan, then apply.** Machine-generated or bulk changes are expressed as a validated plan and applied as one commit. Never DOM automation; never raw Loro writes outside `WorkspaceDocument`. | `planPublish`/`applyPublish` is the existing pattern ✅; it makes changes previewable, undoable, testable, and replayable. | The feature is not shippable as designed. |
| **R3** | **One query engine.** Library facets, board filters, view results, theme selectors, charts, and the agent's `query_cards` consume the *same* query object and evaluator. | Five bespoke filters are five behaviours that disagree; the audit's own warning ✅ ("one query engine, four consumers"). | Do not ship the fifth consumer. |
| **R4** | **One annotation model.** Every annotatable medium (PDF, EPUB, video, canvas region, card field) uses one polymorphic anchor record. | Four highlight formats means four exports, four projections, four broken states ✅ (audit, Bet D). | No new medium until the anchor model exists. |
| **R5** | **Themes are data, not CSS and not code.** Closed token/selector/rule schema; no expressions, no raw CSS, no generated classes, no remote fonts. | Portability, diffability, queryability, and the Tailwind boundary ✅. | Reject the theme. |
| **R6** | **Local-first remains the default.** Every feature must work with the relay unreachable (where it is not inherently collaborative), and must not require a server round-trip to be *correct*. | Principle 1 in `architecture.md` ✅; offline operation is a stated product requirement. | The feature must degrade to a local-only state or be cut. |
| **R7** | **No new object class when a card type suffices.** Cards are the one authored-content object. Media, excerpts, collections, sources: all cards. | Selection, trash, undo, library, references, sharing, projections and exports all key on cards ✅ (ADR-0020 §2). A second class forks all of them. | Model it as a card type or a derived record. |
| **R8** | **Every feature ships tests, projections, and exports.** A feature without all three is a prototype, not a release. | The "demo is the test" tax (§10) is what keeps this list from becoming half-integrated node kinds ✅ (audit, Bet D). | The feature stays behind a flag until the tax is paid. |
| **R9** | **No runtime third-party fetch without explicit link handling.** Metadata comes from importers, not from render-time requests; remote images/embeds go through the existing scheme checks and `referrerpolicy` pattern. | Local-first (R6), privacy, CSP, offline, and outage behaviour all depend on it ✅ (`architecture.md` attachments: allowlisted MIME, `nosniff`, sandbox CSP). | The feature must be link-first with a degraded card. |
| **R10** | **No open-ended value kinds.** No `json` field kind, no arbitrary code blobs, no user-authored expressions in data. | Views, sorting, publishing, redaction and theming all need to *understand* a value ✅ (audit, field-kind critique). | Reject the kind; use a closed shape or a linked record. |
| **R11** | **Every reference-valued thing has an unshared state.** `card` values already render as unavailable/stub ✅; attachments, relations crossing a share boundary, and annotations must do the same. | A viewer must never see a broken box, and must never see a hint of unshared content ✅ (ADR-0022 §5 redaction). | Do not ship the reference kind. |
| **R12** | **Derived stays derived.** View results, section membership, backlinks, resolved styles, and annotations-per-card are computed, never stored as a second truth. Caches must be discardable and rebuildable. | `design-inspirations.md` §4.6 ✅; stored results "will go stale and silently lie". | Redesign as a cache with an invalidation rule, or cut. |

Two corollaries:

- **R13 — No behaviour branch on a type combination.** Types add schema, never behaviour ✅
  (`design-inspirations.md` §4.1a). Built-in media/source/excerpt types must be *data*, not
  `if (typeId === "media")` branches.
- **R14 — Structural writes and text writes have separate undo scopes.** ✅ ADR-0019 §8 and
  ADR-0020. Theme edits, plan applies, auto-arrange, and annotation promotion are structural; they
  must not land in a card's body undo stack.
- **R15 — Instance overrides are a closed token-reference map.** One key per visual property, no
  selectors, no priority, no labels, no freeform values, and no removal of an invariant-bearing
  element (type glyph, direction, focus, selection). They are card-scoped, explicitly `detached`,
  and structural for undo. The theme is the shared grammar; an override is a deliberate exception
  that cannot become a language of its own.

### Gate discipline

- **One gate, one bet.** A gate can unlock several bets; a bet may need several gates.
- **Gates are measured, not asserted.** Each gate names an artifact someone can open. No artifact,
  no gate.
- **A failed gate changes the plan.** If E1 fails, the problem is earlier than V2 and no V2 bet
  starts.
- **No gate is retroactively satisfied** by shipping the feature it was meant to justify.

### 2.1 Gate review, ownership, and expiry

| Item | Rule |
| --- | --- |
| **Owner** | Each gate has an owner *role*, not a named person: the maintainer-operator owns E1–E5 and E8 (product and billing telemetry); the reliability owner owns E2, E3 and E6; the maintainer-operator also owns E7 (the saved-view export). Ownership means producing the artifact, not approving the bet. |
| **Review event** | Gate status is reviewed at every V1 release candidate and at each stage review. No other event opens a gate. |
| **Status register** | A table of `gate → state → artifact link → last reviewed at → affected bets`. States: `unopened`, `measuring`, `open`, `failed`, `deferred`. |
| **Open requires an artifact** | A gate is `open` only when a linked artifact exists and is readable by someone who did not produce it. A verbal report leaves it `measuring`. |
| **Unmeasured deprioritizes** | A gate in `unopened` or `measuring` deprioritizes every dependent bet: they stay in this document and cannot enter a phase. |
| **Expiry** | A gate that remains `unopened` across two V1 releases is treated as `failed`, and its dependent bets are cut from V2 rather than carried forward. |
| **Reopening** | A `failed` gate may return to `measuring` only with a new artifact and a recorded reason the earlier evidence was insufficient. |

## 3. Bet A — Views v2 as the query layer

**Trigger:** E1 + E7. **Precondition for:** B, C, D (charts), E (`query_cards`).
**Status:** ○ proposal. The current shape is ✅ verified; nothing below is implemented.

### 3.1 Where views are today

`savedViewSchema` and `viewQuerySchema` in `packages/graph/src/views.ts` ✅:

```ts
{
  text?: string;          // free text over the search index
  typeIds: string[];      // OR within the group
  tagIds: string[];
  sectionIds: string[];
  scope: "all" | "board";
  groupBySection: boolean;
  order: "relevance" | "title" | "updated";
}
```
- The query "names *what to select*, never what was selected: no card ids are stored" ✅ — the
  comment in `views.ts` is the design rule, and V2 must not weaken it.
- Facets are already "OR within a group, AND across groups" ✅, matching the library.
- The UI is a Views menu (`ViewsBar.tsx`) over that object ◐ audit.

It is a usable starting point but not a sufficient query language. It cannot express "blocked
initiatives with no owner", "claims with no incoming support", or "cards with a PDF but no cover".

### 3.2 The query object, version 2

One object, one evaluator, every consumer. Sketch only — the schema must be closed (R10) and
versioned so saved views migrate.

```ts
interface ViewQueryV2 {
  version: 2;
  text?: { terms: string; scope: "title" | "body" | "both" };
  all: PredicateGroup[];                 // AND across groups
  scope: { kind: "workspace" } | { kind: "board"; boardId: string };
  groupBy?: { kind: "type" | "tag" | "section" | "property"; fieldId?: string };
  order?: Array<{ by: SortKey; dir: "asc" | "desc" }>;
  presentation?: "list" | "table" | "board-filter" | "chart";
}

interface PredicateGroup {
  any?: Predicate[];    // exactly one level of OR
  not?: Predicate[];    // negation applies to the group's matched set
  all?: Predicate[];
}

type Predicate =
  | { p: "type"; ids: string[] }
  | { p: "tag"; ids: string[] }
  | { p: "section"; ids: string[]; subtree: boolean }
  | { p: "property"; fieldId: string; op: PropertyOp; value?: unknown }
  | { p: "text"; terms: string; scope: "title" | "body" | "both" }
  | { p: "presence"; of: "attachment" | "body" | "backlink" | "relation"; fieldId?: string }
  | { p: "relation"; dir: "in" | "out" | "either"; relationTypeId: string; cardId?: string };
```
`PropertyOp` is closed: `eq | neq | lt | lte | gt | gte | in | notIn | between | empty | notEmpty`.
Comparisons are defined **per field kind**, not generically: numbers numerically, dates as instants,
selects by option id, checkbox as boolean, `card`/`attachment` by id presence, text by exact or
substring depending on an explicit op.

### 3.3 Predicate families and what each one buys

| Family | Examples | Requires | Notes |
| --- | --- | --- | --- |
| **Property predicates** | `status is blocked`, `confidence < 0.5`, `targetDate between A and B`, `owner is empty` | Typed field kinds + an index over property values | The single highest-value family ○. Properties are already indexed per card ✅ (§4.2 "scalar properties" belong in the index). |
| **Has / hasn't** | has attachment, has body, has backlink, has any relation, has no cover | Record presence, not value | Cheap and immediately useful; drives "Inbox"-style views. |
| **Relationship traversal** | `linked to <card>`, `no incoming supports`, `has any outgoing relation` | Bet B for the typed form; `kind`/label form works before it | One hop only in v2. No transitive closure, no path queries. |
| **Text scope** | title only vs body only vs both | Existing search index ✅ | Today's `text` searches "titles and bodies" ✅; splitting the scope is a small change with large precision gains. |
| **Selection / state** | selected, trashed, read-only, shared | View state, not document state | State predicates are **not** saved into a view unless the state is durable; "selected" belongs to ad-hoc filters, not saved views. |

### 3.4 Composition limits — resist the boolean AST

A full expression tree (`AND`/`OR`/`NOT`/`XOR`, nesting, parentheses) is the alternative. **Do not
build it.** The audit's position ○ is adopted here:

- **AND across groups** (today's model, already understood by users ✅).
- **One level of OR inside a group.**
- **Negation at group level**, not per predicate, and only for simple cases.
- **No nested groups.** If a user needs nesting, the options are two saved views or a tag.
- **No user-authored expressions.** No arithmetic between fields, no regex syntax, no scripts.

Rationale: a boolean AST is a language, and a language needs a parser, an error surface, a debugger,
a migration path, and documentation. Each of those is a product surface that competes with the canvas
for attention. The 80 % case — "these types, with this status, without this tag, missing this
field" — fits the constrained model. Revisit only if E7 shows repeated failed attempts to express a
query; the likely answer is a **card type**, not operator precedence.

### 3.5 Grouping, sorting, presentation

- **Group by**: type, tag, section (board scope only ✅), or one property. One grouping level.
  Multi-level grouping is out of scope.
- **Sort by**: title, updated, created, section order, or one property, with a per-kind comparator.
  Multi-sort is allowed (two or three keys) but must be stable and deterministic.
- **Presentation**: `list` and `table` first (table = rows of cards, columns of fields ◐ audit, do
  this before any "table field"); `board-filter` next (apply the query as a canvas filter);
  `chart` later (Bet D — declarative spec over a `sourceQuery`).
- A saved view stays a **query + presentation + position**, never results ✅ (`views.ts`,
  `design-inspirations.md` §4.5).

### 3.6 One engine, every consumer

| Consumer | Uses | Must not |
| --- | --- | --- |
| Library facets | The facet subset of the same object | Grow its own filter logic ◐ audit: `libraryFilters.ts` mirrors `UNSORTED_SECTION` already, which is the drift to avoid |
| Board filters | Scope `board` + predicates | Depend on section membership being stored |
| Saved views | The whole object | Store results |
| Theme selectors (Bet C) | `type:`, `tag:`, `prop:`, `rel:` compiled to the same predicates | Implement a parallel matcher |
| Charts (Bet D) | `sourceQuery` in the chart spec | Evaluate in a worker with different semantics |
| Agent `query_cards` (Bet E) | The same object, validated by the same schema | Have its own ad-hoc filters |

If two consumers disagree about a result, that is a **bug in one engine**, not a difference between
features. R3 exists so that consumers cannot diverge.

### 3.7 Derived results and the incremental index

- Results are **derived** ✅ (R12). No result set is written to the document.
- Evaluation must be **incremental**: an in-memory index keyed by `(fieldId, value)` for scalar
  properties, `(tagId)` for tags, `(relationTypeId, direction)` for relations, and the existing text
  index for search ✅-able. A card mutation touches only the affected index entries.
- The index is per-client, discardable, and rebuilt on open; it is never synced and never part of
  undo (same rule as `references` ✅ ADR-0019 §3).
- Deleted/trashed cards are filtered at evaluation, not removed from the index, so trash/restore is
  low-cost and undo-safe.

### 3.8 Acceptance evidence

Bet A is done when **all** of these hold:

1. One `ViewQueryV2` evaluates identically in the library, a saved view, a board filter, a theme
   selector, and `query_cards` (a shared test suite runs the same fixtures through every consumer).
2. Saved views from v1 migrate without loss: every existing facet maps to a predicate; a round-trip
   test proves it.
3. A cold evaluation over a 5,000-card workspace with six predicates stays inside the benchmark
   budget from Bet C's harness (see §5.9), on a mid-range laptop, with the index already built.
4. Incremental correctness: mutating one card changes exactly the expected result sets, proven by a
   property test over random mutations.
5. Trash/restore, undo, and remote edits do not leave stale results (a scenario in Bet E's runner).
6. No consumer can construct a query the schema rejects; unknown operators fail validation loudly.

### 3.9 Explicit limits

- No nested boolean logic, no cross-field arithmetic, no regex authoring, no scripts.
- No transitive traversal, no path queries, no aggregation in the query object (aggregation belongs
  to the chart spec).
- No stored results, no materialized view tables, no server-side query execution in V2.
- No query over card **bodies** beyond the search index; body-scoped text predicates mean "the
  index knows this term", not "parse every body".
- Queries are workspace-scoped or board-scoped. There is no "query across workspaces".

## 4. Bet B — Typed links

**Trigger:** Bet A shipped (predicates exist) + E4 if relations cross shares. **Blocks:** nothing.
**Status:** ○ proposal that would supersede part of ADR-0019 ✅.

### 4.1 The finding

Two verified facts collide:

- `graphEdgeSchema` includes `boardId` ✅ (`packages/graph/src/schema.ts:172-186`) — "Links belong to
  the board they were drawn on". Kinds are `references | relates-to | tagged`; paths are
  `bezier | straight | step | smoothstep` ✅.
- Views are workspace-scoped ✅ (`scope: "all" | "board"` in `views.ts`).

So a workspace view asking *"what supports this claim?"* must walk every board, dedupe drawings of
the same statement, and accept that **a relation which was never drawn does not exist**. Meaning
currently lives in three places ADR-0019 chose ✅: mentions, `card`-valued properties
whose *name* is the semantics, and free-text edge labels/descriptions.

The gap typed links close is **queryability**, not colour. A relation that exists only as a drawing
is invisible to a workspace query; a relation that exists only as a property value is invisible to
the canvas.

### 4.2 Three options, ranked

| Option | Shape | Cost | Query semantics | Verdict |
| --- | --- | --- | --- | --- |
| **A. `relationTypeId` on edges** | Board-scoped typed drawings; identity for queries = `(source, target, relationTypeId)` | Low: one optional field + a `relationTypes` registry; **no migration** ✅ (the escape hatch ADR-0019 pre-authorized) | Must dedupe across boards; an undrawn relation does not exist | **Ship first** ○ |
| **B. `relations` root + edge drawings** | Workspace-level relation records; edges reference `relationId` | High: migration, undo scopes, projections, publish, backlinks, redaction | Clean: one statement, many drawings; undrawn relations are first-class | **Ship second, when multiplicity is real** ○ |
| **C. Relations only, no drawings** | Replace edges with relations rendered everywhere | Very high | Clean | **Rejected** — it deletes the spatial canvas, which is the product ✅ |

The deciding question is not "types yes/no"; it is **"is a relation a statement (workspace) or a
drawing (board)?"** ADR-0019 answered "drawing" because nothing queried it ✅. Bet A queries it.

Option B becomes correct the moment "the same statement drawn on two boards" is a real user need —
which is exactly the open question already recorded in `design-inspirations.md` §11 ("Edge placement
multiplicity: one drawing per (board, relation)") ✅.

### 4.3 The `relationTypes` record

```ts
interface RelationType {
  id: string;              // stable workspace id, never a name
  name: string;            // "Supports"
  inverseName?: string;    // "Supported by" — renders on incoming edges
  direction: "directed" | "symmetric";
  sourceTypes?: string[];  // advisory only
  targetTypes?: string[];  // advisory only
  createdAt: string;
  updatedAt: string;
}
```
Not included: `color`, `glyph`, `width`, `style`, `constraints`, `required`.

### 4.4 Design rules

| Rule | Statement | Reason |
| --- | --- | --- |
| **Never require a type** | A drawn edge may stay untyped; the picker defaults to last-used and always offers `relates-to` | Decision fatigue is what killed the first attempt ✅ ADR-0019 |
| **Constraints are advisory** | `sourceTypes`/`targetTypes` warn, never block a write | Matches required fields, which are advisory ✅ (`design-inspirations.md` §4.1a) |
| **No colour on relation types** | Visual encoding belongs to the theme (Bet C) | Otherwise the theme system and the relation registry fight over one axis ○ |
| **Deletion is dormancy** | Deleting a type leaves its relations in place, untyped | Matches types, tags, and fields, which go dormant rather than cascading ✅ |
| **`direction` is semantic; `bidirectional` is a drawing** | They are different axes: what the statement means vs. how the arrow is drawn ✅ | `bidirectional` is already a per-edge drawing property (`schema.ts`) ✅ |
| **`label` stays per-drawing** | The free-text description is an annotation on the drawing, not the type | ADR-0019 §1 added descriptions ✅; do not migrate them into types |
| **Ids are stable** | Renaming `Supports` does not touch any edge | Field-granular writes ✅ R12/§4.7 in design doc; whole-record writes break concurrent edits |
| **Backlinks union** | Mentions, `card` fields, `relation` fields, placements, and edges all read as one derived list | ADR-0019 §4 ✅; no new backlink store |

### 4.5 The `relation` field kind is a **view over relations**, never a store

This is the load-bearing rule. Without it, V2 has two stores for one fact.

```ts
{ id: "contradicts", name: "Contradicts", kind: "relation",
  relationTypeId: "contradicts", multi: true }
```
- **Read:** lists relations of that type where this card is the source (and, for `direction:
  "symmetric"`, either end), rendered with the inverse name for incoming.
- **Write:** creates/removes a relation record — one commit, one undo step, structural scope (R14).
- **The relation record is the only store.** The field never holds values. This is the same rule
  ADR-0019 already applies to property blocks: "a property block in the body is a view, never a
  store" ✅.
- **`card` stays** for single-valued, attribute-like pointers ("Owner", "Success metric", "Parent
  epic"). If the answer is naturally one card, it is not a relation.

The field kind also gives the UI the thing users actually asked for ○: a card panel with a
"Contradicts" row next to a "Comments" row, without inventing a second relation system.

### 4.6 Migration and coexistence

1. Add the `relationTypes` registry and `relationTypeId?` to `graphEdgeSchema`. **No migration, no
   schema bump for existing edges** ✅ (ADR-0019's stated escape hatch).
2. **Suggest types from existing labels.** If three edges say "supports", offer "Create relation
   type *Supports* and bind these 3 drawings". Bind is explicit; unmatched edges stay untyped.
   This is an upgrade prompt, never a rewrite.
3. `kind` remains for the three coarse buckets and for old data; `relationTypeId` refines it. Both
   may coexist on one edge; predicates prefer `relationTypeId` when present.
4. Backlinks keep working unchanged ✅: union of mentions, `card` fields, `relation` fields,
   placements, edges.
5. If option B arrives later: derive one `relations` row per distinct
   `(source, target, relationTypeId)`, point edges at `relationId`, keep `source`/`target`
   denormalized on the edge for fast rendering and orphan tolerance. The migration is computable
   from existing data, which is why A is safe to ship first.

### 4.7 What breaks if the field-as-view rule is skipped

| Symptom | Cause |
| --- | --- |
| Backlinks double-count one fact | Property value *and* relation record both exist |
| Views and properties disagree | Two evaluators over two stores |
| Publish has two conflict models for one change | Body/field conflict vs. relation conflict |
| Themes style one and not the other | Selector matches a store, not a meaning |
| Export contains two representations | JSON/Markdown emit both |
| Agent plans create both | The plan schema exposes both as writable |

This is the difference between "typed links" and "a second, parallel relation system" ◐ audit.

### 4.8 Gate and ADR plan

- **Hard gate:** view predicates (`has relation`, `no incoming relation`, `linked to`) must ship
  **before or with** relation types. Shipping a type picker with nothing to query is the exact
  failure ADR-0019 rejected ✅.
- **ADR required:** "Relation types supersede ADR-0019's no-relation-types decision, because a query
  layer exists". It must record what changed, keep the references half, keep the view-never-store
  rule, and state the field-as-view constraint.
- **Acceptance:** a saved view answers "claims with no incoming supports" correctly across two
  boards and across an undrawn relation; a share projection redacts a relation crossing the boundary
  into a stub (R11); undo of a relation write removes exactly one relation.

## 5. Bet C — Visual grammar and themes

**Trigger:** E1 + E7. **Depends on:** Bet A (selectors compile to the same predicates).
**Status:** ○ proposal. Current styling facts are ✅ verified.

### 5.1 Verdict

> **A constrained version belongs at the v1.1/v2 boundary. A full authoring studio belongs nowhere
> near V1, and probably not in V2.** ○

**Ship:** tokens, semantic selectors, per-property rule resolution, relationship styling by `kind` +
controlled label (then `rel:` once Bet B lands), three or four built-in themes, import/export *with
binding*, a resolved-style inspector, accessibility guardrails.

**Do not ship:** a Bricks-style visual rule builder, a marketplace, per-canvas variants and
inheritance, arbitrary CSS, remote fonts, animations, background images, selector expressions,
theme-driven data semantics, and per-node styling **that can replace the theme or carry meaning**.
A closed, token-referencing per-card override layer is explicitly *not* that rejection: it is the
last, visibly detached layer of the same model (R15).

"Visual grammar" is the name for this model: styles are defined over graph concepts, so the same
card type and relationship look the same on every board. Per-node styling as the primary model does
not do that ◐ (audit).

### 5.2 The model

```
tokens -> selectors -> rules -> instance overrides

tokens     closed, mode-aware values (light / dark / shared)
selectors  graph predicates: type:, tag:, prop:, rel:, state:, scope:
rules      selector + token assignments + priority + label
instance   per-card overrides: the exception, visibly "detached"
```

**Tokens** (closed, ~40 max): background, ink, muted ink, border, accent, selection, radius, shadow,
stroke width, dash, font family/size/weight, density, plus a few semantic colours (`danger`,
`success`, `warning`). Concrete values, no expressions.

**Selectors** are over graph concepts, never DOM classes or Tailwind utilities:

| Selector | Matches | Source |
| --- | --- | --- |
| `type:<typeId>` | Cards of a type | `primaryTypeId` ✅ |
| `tag:<tagId>` | Cards with a tag | tag keys ✅ |
| `section:<sectionId>` | Derived membership, board scope | `sectionForCard` ✅ |
| `prop:<fieldId> <op> <value>` | Property predicate | Bet A |
| `rel:<relationTypeId>`, or `edge.kind` before Bet B | Relation drawings | Bet B / `edgeKindSchema` ✅ |
| `state:selected \| dimmed \| trashed` | View state only | UI state |
| `scope:workspace \| board:<id>` | Where the rule applies | Context |

**Rules** carry `id`, `label`, `priority`, `when` (selector), `set` (token → value). Resolution is
**per property, not whole-style replacement**: a tag rule that sets background must not erase a type
rule's border. Cascade layers are fixed and visible — `base < type < tag < property < relationship <
instance` — with numeric priority inside a layer and a deterministic tie-break (rule id) so two
clients resolve identically.

**Instance overrides** are card-level, not placement-level: the card is the object, a placement is
board-specific ✅ (ADR-0020 §2). The existing `overridden` flag in `DisplayStyleDialog` is the
precursor ◐; reuse the idea, not necessarily the storage.

The two layers have deliberately different jobs:

| | Theme rules | Instance override menu |
| --- | --- | --- |
| **Job** | Consistency across many cards | Expression for one card |
| **Author** | Theme author / workspace admin | Any editor (capability-gated) |
| **Scope** | Selector (`type:`, `tag:`, `prop:`, later `rel:`) | One card id |
| **Vocabulary** | Full token set + priority + label | Closed token subset + enumerated modifiers; no priority, no selectors |
| **Effect** | Many cards | Exactly one |
| **Theme change** | It *is* the theme | Survives as an explicit `detached` override |
| **Inspector** | "Winning rule: `type:Claim`" | "Detached: `bg → $danger`" |
| **Undo** | Structural, theme-scoped | Structural, per card |

The surface is right-click → **Style**: Reset to theme; Background (`Surface`, `Muted`, `Accent`,
`Danger`, `Success`, `Warning`); Ink (`Strong`, `Muted`); Border (`None`, `Hairline`, `Strong`,
`Accent`); Density (`Compact`, `Comfortable`); Weight (`Quiet`, `Emphasis`). Every item shows a
swatch and the resolved token name. The menu must state that the style applies to the card
everywhere; board-only emphasis belongs to a section or a theme rule. The open value set cannot grow
into opacity, shadows, gradients, per-corner radius, or a colour picker without a new token and a
pass of the desaturate test.

### 5.3 Absorbing the styling system that already exists

Four partial styling systems exist today ✅. A theme system beside them would be a fifth source of
truth, so the migration decision must be explicit:

| Existing surface | Today | Theme treatment | Who wins |
| --- | --- | --- | --- |
| `CardType.color` / `glyph` ✅ | Type-level colour and icon | Seeds the `type:` layer's default tokens | **Theme at render**; the type record stays the data default |
| `FieldDefinition.display` ✅ | Per-field display template | A presentation token binding for that field's value | **Field wins** for its own value; the theme styles the container |
| `DisplayStyleDialog` field vs. instance ✅ | Field-wide vs. instance override + overridden flag | Instance layer; the flag becomes "detached from theme" | **Instance wins** (last layer), always visibly detached |
| Fixed `sectionColors` / `edgeKinds` / `edgePaths` ✅ | Enumerated colours, kinds, paths | Theme supplies values for the same enum members | **Theme wins**; the enum keeps data valid without a theme |
| CSS vars `--surface`, `--ink`, `--hairline`, `--card-shadow`, `.dark` ✅ | App-wide | Split: app tokens stay on the shell, canvas tokens are theme-scoped | **App wins on chrome; theme wins inside the canvas** |

The rule, written down before building: **the theme is the renderer of first resort; stored type and
field values are defaults it may override; instance overrides are the exception.** Anything else
produces "why is my Claim card blue when the theme says green?", which no inspector can explain.

### 5.4 Portability is a binding problem, not a JSON problem

`type:Claim` is human-readable; internally everything is a workspace-scoped id ✅. A theme exported
from one workspace and imported into another must map *ids*:

```json
{ "kind": "suite.theme", "version": 1, "name": "Review",
  "requires": { "types": ["Claim", "Evidence"], "tags": ["hypothesis"],
                "fields": [{ "name": "status", "kind": "select" }], "relations": ["supports"] },
  "tokens": { "light": {}, "dark": {}, "shared": {} }, "rules": [] }
```
1. `requires` declares what the theme assumes.
2. Import shows a **mapping wizard**: "expects `Claim` → map to your type ▾ (or create it)".
3. **Never auto-create** types, fields, tags, or relations without one click per item.
4. Store the result as `themeBindings` **in the workspace**, not in the theme file.
5. **Partial application is explicit**: unbound requirements are listed, and dependent rules are
   inert rather than silently dropped.

Without this, themes only work between workspaces that already share an ontology — a much smaller
surface than "themes as distribution" implies ◐.

### 5.5 Relationship theming needs a vocabulary first

`rel:supports` **does not exist** in the current schema ✅; the vocabulary is `kind` (three values)
plus a freeform `label`.

- **v1.1 / early V2:** style by `edge.kind` plus a **controlled label match**, with a visible warning
  that renaming the label breaks the rule. Call it "relationship kind", never a type.
- **After Bet B:** `rel:<relationTypeId>` becomes real and binds through `themeBindings`.
- **Never** ship `rel:` first. A selector that matches nothing teaches users the feature is broken.

### 5.6 Mode-aware tokens and accessibility

App mode is global (`light`/`dark`/`system` in `localStorage`, `.dark` on `<html>`) ✅, so a theme
cannot just set "card background = white".

```ts
tokens: {
  light:  { cardBg, ink, border, accent },   // per-mode
  dark:   { cardBg, ink, border, accent },
  shared: { radius, strokeWidth, font, density }
}
```
Resolution: **app mode → theme mode tokens → rule tokens → instance overrides.** A theme may omit
`dark` and inherit the app's dark base; if it does, it must not force light-only colours.

Guardrails, enforced at import **and** render: minimum contrast for text and focus rings; colour is
never the only encoding of a meaning-bearing value; focus and selection stay visible regardless of
theme; a **local** high-contrast / reduce-theme override that never mutates the shared theme;
readable errors for unknown tokens, unknown selectors, and over-cap rules.

### 5.7 Themes must travel

| Path | Required behaviour |
| --- | --- |
| **Share projections** ✅ (ADR-0022/0023) | Copy the theme or its resolved subset with the shared content, or a shared board looks like a different product. Selection shares too. An instance override travels as a token *reference*, and the projection carries the theme (or its resolved subset), so the viewer sees the intended look without a frozen style snapshot. |
| **`.suite` export/import** ✅ | Themes and `themeBindings` travel; import re-runs the wizard if the ontology differs, or "exact backup" restores a different-looking document. |
| **Readable JSON / Markdown** | Themes as data, not resolved styles; a consumer without the theme still reads the content. |
| **Undo** | Theme edits are **structural** with their own scope (R14); they never enter a card's body undo. |
| **Sync conflicts** | Per-rule, per-token writes with stable rule ids. Never whole-theme replacement — that is the whole-record write §4.7 of the design doc forbids ✅. |
| **Projection rebuild** | A theme change rebuilds affected projections, debounced per workspace, not per rule. |

### 5.8 Scope: the canvas, not the app

Theme variables are set on the **canvas root** (pane, nodes, edges), never on
`document.documentElement` ◐. The shell keeps its own tokens ✅. So contrast checking stays bounded,
a user cannot render the app unusable, and the implementation is one subtree rather than a global
cascade.

### 5.9 Performance model

Reuse the existing architecture rather than inventing a style engine:

- **Index rules by selector key** — `typeId → rules`, `tagId → rules`, `fieldId → rules`,
  `edgeKind → rules`, plus a "matches everything" list, so a card evaluates only its candidates.
- **`StyleResolver` keyed by `(record identity, theme revision)`**, using the identity-stable records
  the snapshot store already hands out ✅. Invalidate only when the card's type/tags/properties/
  override or the theme revision changes.
- **One theme revision counter.** Any edit bumps it; styles recompute lazily on read, never by
  walking every card synchronously.
- **Lazy per visible node**, honouring `onlyRenderVisibleElements` ◐.
- **CSS variables on the element, not generated classes**: `--card-bg`, `--card-ink`,
  `--card-border`, `--edge-stroke` on the node/edge root; React re-renders only when the resolved
  style object identity changes.
- **SVG marker strategy**: generate a small set keyed by `(colour, width, direction)` or use
  `context-stroke`; cap unique markers to avoid DOM bloat.
- **CI budget**: the default thresholds are hypotheses adopted now so the benchmark can be written
  before E3 measures anything: **5,000 cards × 100 rules at ~20 % match, changed-card resolution
  < 1 ms, theme switch < 100 ms to first visible style** ○. They are marked ○, implemented as test
  constants, and tuned by E3 rather than argued about.

**Caps, validated on import:** ~200 rules, ~6 predicates per selector, ~40 tokens. The purpose is
to bound the worst case: a rule set at the cap still resolves by candidate list, never by a full
scan.

### 5.10 Semantic invariants — the line a theme cannot cross

- Direction is always visually encoded, even if the theme styles it.
- Relationship labels and type glyphs are always present; themes style, never hide.
- Meaning-bearing values (status, confidence) are text-readable, never colour-only.
- Focus and selection are always visible, independent of theme.
- Trash, read-only, and share states stay legible: a theme cannot make a read-only surface look
  writable.
- A theme cannot change semantics — no rule that alters which card a relation points at or hides a
  card from a view.

### 5.11 The Tailwind boundary

| Layer | Who uses it | What they see |
| --- | --- | --- |
| App UI | Developers | Tailwind utility classes |
| Theme tokens | Theme authors | Named token dropdowns (`$cardBg`) |
| Theme rules | Ordinary users | `type:Claim` → `$cardBg` |
| Canvas render | Runtime | CSS variables / inline attributes |

Tailwind 4's `@theme` maps **app** tokens to CSS variables for the app's own components. Users never
type `bg-[oklch(...)]`, never see a class name, and themes are never compiled to Tailwind. The reason
is mechanical: Tailwind classes are build-time, user rules are runtime, and exposing utilities means
either a giant safelist or a fallback to inline styles — which defeats the purpose ◐.

### 5.12 The desaturate test

> **If you desaturate the canvas, can you still read the structure?**

If yes, the theme carries structure. If no, the theme changes only appearance. This test is the
acceptance criterion for the whole bet, and it is what keeps V2 from shipping a skin marketplace ○.

### 5.13 Ship / defer

| Ship | Defer |
| --- | --- |
| Token layer, light + dark, closed set | Full visual rule builder |
| Selectors: type/tag/section/property/edge-kind/state/scope | Selector expressions (OR/NOT/regex/nesting) |
| Per-property resolution + priority + label | Marketplace / gallery |
| Instance overrides with a "detached" indicator, closed vocabulary, no freeform editor | Per-canvas variants and inheritance |
| 3–4 built-in themes, each teaching a feature | Per-user themes (except local a11y overrides) |
| `.suitetheme` import/export with binding wizard | Arbitrary CSS, remote fonts, animations, background images |
| Resolved-style inspector | Theme-driven data semantics |
| Contrast/focus/colour-blindness guardrails, local high contrast | Auto-creating types/relations on install |
| Relationship styling by `kind` + controlled label | `rel:` before Bet B |

**Acceptance:** a built-in theme applies to a real starter workspace; an incomplete theme imports
with a visible unbound list and applies partially; the inspector names the winning rule per
property; desaturating preserves structure; the 5,000-card benchmark holds; a share projection
renders with the theme intact; undo of a rule edit is one step; an instance override is one
structural commit, survives a theme edit as `detached`, cannot remove an invariant-bearing element,
and a projection carries its token reference rather than a resolved snapshot.

## 6. Bet D — Sources, media, and annotations

**Trigger:** E8 + E1, plus E4 for redaction and E2/E6 for storage. **Depends on:** Bet A, Bet E
(fixtures). **Status:** ○ proposal; storage/allowlist facts ✅ verified.

### 6.1 Rationale

> **Read / watch / listen → extract → think.** ○

One workflow, extending the type system rather than building a parallel media product. It is the
cluster the audit ranked highest: **Add Media + annotations + excerpt cards + expanded Views**. It is not "a PDF
editor", "a video player", or "a media library" — the Suite feature is that extraction lands in the
graph, where it can be linked, queried, themed, and shared.

### 6.2 Four primitives

| Primitive | What it is | Where it lives | Why |
| --- | --- | --- | --- |
| **Objects** | Cards | Workspace document ✅ | One authored-content class (R7) |
| **Sources** | Bytes or an external record beside the doc: image, PDF, EPUB, video, URL, provider record | Bytes beside the doc ✅, metadata in the doc | Keeps CRDT state small and projections redactable ✅ (`architecture.md` §Attachments) |
| **Annotations** | `{ id, sourceId, anchor, body?, color?, authorPresenceId }` | Workspace root, keyed by id | High volume, geometry-anchored, referenced by many cards |
| **Scenes** | Ordered camera + emphasis states over a board/view | Workspace root | Presentation, tours, handbook steps |

The anchor is **one polymorphic union** — the decision the audit says to make before any medium
ships ◐:

```ts
type Anchor =
  | { kind: "page"; page: number; rects: Rect[] }                    // PDF
  | { kind: "quote"; quote: string; prefix: string; suffix: string } // EPUB / HTML
  | { kind: "time"; startMs: number; endMs: number }                  // video / audio
  | { kind: "canvas"; boardId: string; x: number; y: number; w: number; h: number }
  | { kind: "card"; cardId: string; fieldId?: string };               // a note on a card
```
Without one union, V2 gets four incompatible highlight models, four export paths, and four projection
stories ◐. Every new medium must be *a renderer plus a `kind`*, not a subsystem.

### 6.3 Add Media — highest-value idea

**Do it, but as a card type, not a new entity** (R7).

- A built-in `media` / `source` **card type** defined as data (fields + defaults + template + landing
  place) — never an `if (typeId === "media")` branch (R13).
- A **Dock affordance** beside the existing Library and type menu ◐ (`Dock.tsx` is the seed).
- Drag/drop and paste route to the **same** handler; the card lands on the active board with the
  appropriate viewer block in its body.
- Capability-aware: hidden or disabled in read-only/share sessions unless the role may create content
  ✅ (ADR-0022 §6, S7 revision: board editors may create, card editors may not).

The real work sits behind the affordance: `attachments.ts:22-36` is an **image-only MIME allowlist**
with a **16 MiB** cap ✅, one BLOB column, one SQLite file. PDF/video need range requests, thumbnails
and object storage — the interface is explicitly the object-storage seam ✅, so use it before the
table grows. Every new node kind must enter `RICH_TEXT_NODE_ATTRIBUTE_NAMES` ✅ and the
`publishValidation.ts` checks, or publishing rejects it and `editorSchemaContract.test.ts` fails.
Projections copy metadata only; a shared board resolves bytes through the relay, as images do today
✅.

### 6.4 The `attachment` field kind

A reference, not a value blob: `{ id, mime, name, width, height, bytes }` — the shape the inline atom
already carries ✅. It reuses `propertyValueError`, `formatProperty` and publish planning ✅, and
immediately enables "cover image" on a book, "source PDF" on a claim, "trailer" on a film, plus `has
attachment`/`no cover` filters (Bet A) and table thumbnails. **Never bytes, never a nested mutable
media object** — one record, many references. It **must define an unshared state** (R11: "bytes not
shared" / "local only"), rendered like the `card` kind's unavailable state ✅. **No open-ended `json`
kind** (R10) — it would kill views, sorting, publishing, and the schema guarantee ◐.

### 6.5 Annotations are a root, not a field kind

An "Annotations" field next to a "Comments" field is the wrong model for four reasons ◐: **lifetime**
(created in a viewer, independent of any card, referenced by several), **volume/write pattern**
(hundreds of highlights, record-granular not whole-value LWW), **geometry** (renderer state, not card
property), and **projections** (a share must redact annotations on cards it excludes — a filter over a
root, not a schema problem).

- `annotations` root keyed by id, each with `sourceId` + a polymorphic anchor.
- Surfaced on a card as a **derived section**, exactly like `references` ✅ — computed, not stored.
- **Promote to excerpt** is one-way and idempotent: copy the quote into a card of type `excerpt` with
  a `source` card field and an `annotation` id, then set `annotation.cardId`. The annotation remains;
  no dual truth.
- **Comments stay separate**: `LoroList` threads rooted at a card/field/anchor, with their own
  retention and redaction. A comment is a conversation; an annotation is a mark.
- **Three projection cases, each with an explicit rule:**
  1. *Source and annotated cards both in the share* — annotations are copied with the projection.
  2. *Source in the share, annotated cards outside it* — the annotation is copied for its anchor and
     excerpt text, but the card reference is a stub: the viewer sees "annotation on a private card",
     with no title, no navigation, and no field values.
  3. *Shared source whose annotated cards are only partly in the share* — annotations on included
     cards are copied in full; annotations on excluded cards are reduced to anchor-only records
     (page/time/region plus the annotation body if it was authored on the source), never the card's
     identity or properties. The projection must not leak the existence of a card the share excludes
     beyond "an annotation exists here". The same rule applies in reverse: an annotation whose
     `sourceId` is outside the share is dropped entirely, because the viewer cannot render the
     anchor.
- Undo: creating/moving is structural, editing the annotation body is text-scoped (R14).

### 6.6 Views expansion

Also Bet A, and part of this phase by sequencing: "cards with a PDF, no cover, status unread" is the
query that makes media useful.

### 6.7 Scenes and presentation mode

> **Naming (2026-10-25).** A "scene" here is a saved presentation — viewport, card ids, caption — not
> the removed scene *surface* ([ADR-0036](../decisions/0036-the-canvas-is-react-flow.md)). It is built
> on the React Flow camera and needs no projection layer.

Low-cost, because `focusTarget` and camera animation already exist ✅ (`useUiStore.ts`,
`CanvasBoard.tsx`).

```json
{ "id": "s3", "boardId": "roadmap", "viewport": { "x": 0, "y": 0, "zoom": 1 },
  "cards": ["c1", "c2"], "dimOthers": true, "caption": "The two bets that block Q4" }
```
Scenes are a workspace root; presenting advances through them, animates the camera, dims others. No
slide engine, no second rendering model. This one feature gives presentation mode, guided tours,
handbook "point at this" steps, and a clean agent target (`scene_apply`).

### 6.8 Walkthroughs and tutorials

Two layers, one format. **Product tours** anchor to existing `data-testid` attributes ◐, are versioned
against the app version, and fail a CI test when an anchor disappears — the only defence against tour
rot. **User-authored walkthroughs** reuse scenes + captions instead of a second tour format. Both stay
local and offline; never fetch a remote tour script (R9: supply chain, CSP).

### 6.9 Dynamic handbook

Docs-as-data: a `handbook` record of sections, each optionally scoped to a type, field, or view, with
`{{}}` references resolved against the workspace (counts, names, examples), rendered as an in-app
drawer. **It must not become a CMS** ✅ (`design-inspirations.md` non-goals): no routes, slugs, sitemap
or site tree. User-added docs attach as cards of type `doc`, so they stay inside the object model,
search, sharing and export.

### 6.10 Integrated chat

"Basically free with Loro" is half true ○: transport and merge are free, the product is not.

| Question | Options | Leaning |
| --- | --- | --- |
| **Location** | In the workspace doc vs. a separate room | **Separate room** — in-doc chat bloats every projection and export, and complicates retention/redaction |
| **Shape** | `LoroList` of messages: stable id, author presence id, timestamp, optional card/annotation ref; edits/deletes are list ops; reactions nested maps | `LoroList` |
| **Ephemeral vs persistent** | Typing/cursors in `EphemeralStore`, messages persist | Split, matching presence ✅ |
| **Sharing** | Board/card shares must not carry workspace chat | Redact in projections or scope per share |
| **Notifications** | Need a server and an identity | Not in the first pass |
| **Retention** | A paid-plan question before the first invoice | Decide before charging |
| **Scope** | Workspace vs. board | **Board-scoped first**; `@card` mentions reuse existing machinery |

Chat is a medium, not the product: do not turn Suite into "chat with your notes" ○.

## 6.10a Pinned for a later stage

Three ideas raised on 2026-10-25, deliberately **not built yet**. They are recorded with enough
detail to pick up without re-deriving the reasoning, and nothing in the current stage depends on
them.

### Pinned A — Arrange on a selection

**Now:** the canvas context menu no longer offers *Arrange fractally*. Fractal layout applied to the
whole board without being asked, which is a mode, not a gesture — and it is gone from the menu.

**Next stage:** **Arrange** acts on a multi-selection — the cards (and later the boards) the user
picked. The engine already exists and keeps its tests: `packages/scene` (`layout.ts`) plans, and
`apps/canvas/src/canvas/layoutCommand.ts` maps a plan onto a graph `LayoutPlan` that
`applyLayoutPlan` commits as one undoable batch. What is missing is the gesture and the chooser:

- The menu entry appears only with a multi-selection (two or more cards), and names the count.
- A small picker for the pattern and spacing; the default is the grid, the rest stay one click away.
- Selection scope: arrange the selected cards inside the selection's own bounds, so an arrange never
  reflows the rest of the board.
- Board-level arrange (several boards, later) is a separate recipe over board frames, not cards.
- Acceptance: one undo step per arrange; pinned/locked cards unmoved; a section's membership after
  the arrange explained in the UI (the geometry consequence ADR-0017 already states).

### Pinned B — Links across boards, sections and cards

**Now:** a Link is a drawn arrow between two cards **on one board** (ADR-0006/0007/0008). A
reference — a mention or a `card` property — can cross boards, because it is not spatial.

**Next stage:** make the *relationship* first-class across containers: a link whose endpoints are a
board, a section, or a card, and whose middle can span boards. Open questions to settle first:

- **Not a second edge store.** ADR-0019 rejected typed links as a separate model. A cross-board link
  is either an edge whose `boardId` is the board the gesture happened on, with endpoints resolved
  per instance (ADR-0030's instance rule, now withdrawn with the scene) — or a reference row, and
  the answer decides whether it renders as a line at all.
- **Where does it draw?** A link to a card on another board has no shared canvas. The honest
  options are: draw it to the *portal* that leads there, show it only in the References panel, or
  draw a stub with the target's title. Choose one; do not invent a second canvas.
- **Section endpoints are derived.** A section is a spatial region, not a record (ADR-0017). A link
  to a section means "to this region as it is now" and re-anchors when the region moves; a link to a
  card *inside* it is not the same statement.
- **Cycle and multiplicity** are already legal in the document; the renderer must not care.
- **Shares** must classify the new endpoint kinds in every projection (ADR-0022), with an
  out-of-scope target reading as unavailable rather than silently missing.

### Pinned C — Whiteboards become Sketches

**Now:** `whiteboard` is a card type with an Excalidraw surface, a live SVG face and a preview
(ADR-0031). The name promises a second canvas; the use is a quick drawing on a card.

**Next stage:** rename the concept to **Sketches** — a small drawing that belongs to one card and
shows its content on the board face. The rename is the cheap half; the real question is the shape:

- **Card type vs field kind.** A drawing as a `sketch` **field kind** would make it one value of a
  card, like a `card` or `board` reference: the card stays the object, the sketch is a property, and
  a type can hold one without becoming a drawing. The cost is the `attachment`-style 14-surface tax
  (validation, portable export, publish allowlist, projection redaction, template blocks).
- A field kind also composes: a "Concept" card with a `sketch` and three text fields is one card
  instead of a card plus a nested drawing. A card type cannot do that.
- Keep the stable type id (`whiteboard`) in the document either way; only the label and the type
  name change, so existing workspaces migrate by display name, not by data move.
- Decision needed before any code: **is a sketch the card's face or a value on the card?** If the
  former, keep the card type and rename it. If the latter, add the field kind and deprecate the type
  (additive first, per the schema rule).

### 6.11 Layout, grid, mindmap, and grouping

> **Arrange is pinned to a selection** (§6.10a Pinned A). The whole-board *Arrange fractally* menu
> entry was removed on 2026-10-25; the planner it used is kept as the engine for the selection
> gesture.

**Portals (nested canvases) moved to [Alpha A11](./alpha.md#74-a11--portals-and-card-focus-pinned).**
The data model is ADR-0029 and it ships: a portal card with a `board` field and a live miniature.
The live, scaled instance inside a derived scene was A11a and is **withdrawn**
([ADR-0036](../decisions/0036-the-canvas-is-react-flow.md)); A11b, the fractal layout command,
continues on the React Flow board. This section keeps the later layout/grouping and cross-board-edge
work.

This conflicts most directly with existing invariants, so its scope is constrained ◐:

- **Auto-arrange is a command, not a mode.** Compute a plan, apply via `movePlacements` in one commit,
  one undo step, conflict-safe. Never a per-frame layout engine writing placements — that violates
  "no high-frequency CRDT" ✅ and fights every remote peer.
- **Fractal recipes are the same command.** A recipe declares a pattern (grid, columns, rows, radial,
  spiral, phyllotaxis, rings, treemap), spacing, alignment and ordering, plus per-depth overrides
  (scale, gap, rotate, pattern). It recurses through portals by default, previews the plan, and
  applies as one field-granular batch and one undo step. Deterministic; optional seeded jitter.
  Cycles stop at the repeated board path, pinned cards keep their positions, and nothing reflows while
  the user works. On the React Flow board a recipe applies to the active board, because portals are
  doorways rather than expanded instances.
- **Grid/list placement on drop is fine**; a persistent reflowing "layout mode" is not.
- **Sections already are spatial grouping** ✅ (ADR-0017: derived from header anchor, nesting by
  containment). No third container entity.
- Explicit non-spatial grouping = a **`collection` card type** with `contains` edges — still cards (R7).
- **State the geometry consequence**: any layout that moves cards silently changes section membership ✅.
  Correct, but it needs a visible explanation and a test, or users report "cards jumping sections".

### 6.12 Renders and visualizations

A **chart node with a declarative spec** (`chart`, `dimension`, `measures`, `sourceQuery`) — not a code
blob, not an arbitrary Vega-Lite document, not custom JS. The spec lives in the doc; rendering is
client-side, deterministic, and **derived from a view query** (Bet A), so charts stay live while
results stay unstored (R12). Register the node in the publish allowlist ✅ and schema contract; export
a static fallback (SVG/PNG inside `.suite`). **Accessibility:** every chart ships a data table or an
`aria-label` summary. **No eval, no remote render, no third-party data at render time** (R9).

### 6.13 PDF first, EPUB later

The feature is **highlight → excerpt card → backlink → cite**, not "open a PDF" ◐.

- **PDF (V2):** pdf.js + text layer; anchors are page-indexed rects plus a small `fingerprint` (file
  hash) so a replaced file cannot re-anchor onto wrong text; bytes beside the doc ✅, annotations in
  the doc, metadata only in projections; excerpt promotion copies quote + page + a reference back to
  the source card, so backlinks and citations need no new mechanism ✅.
- **EPUB (V2.5+):** reflowable → **text-quote anchors** (`quote`, `prefix`, `suffix`), not CFI, which
  is brittle across renderers and re-paginates; **reject DRM explicitly in the UI**; a **separate
  renderer project**, not a PDF variant.
- Shared prerequisites: object storage, signed reads, range requests, and a legal/ToS posture. Users
  will upload books they do not own: process locally or in user storage where possible, build no
  sharing path for uploaded books, keep the ToS boundary explicit.

### 6.14 Video

**Link-first (V2):** YouTube/Vimeo embeds + `time` anchors + captions/transcripts → searchable
excerpts. No transcoding, no CDN economics, most of the value. **Uploaded video (later):** thumbnails,
transcoding, range streaming, CDN, and a storage bill that changes pricing — only if E8 shows demand.
The `time` anchor is the same union member as PDF and audio; that is the payoff for §6.2.

### 6.15 Table: view now, field later

- **Table view of cards** — rows = cards, columns = fields. "Expand views" plus a renderer: high value,
  no new schema. **Do this.**
- **Table field** — a card holding a grid of typed cells. Needs its own schema, **cell-level CRDT
  writes** (whole-value replacement is a conflict disaster), publish planning, export and redaction.
  **Not before the table view**, probably not in V2. It is not a mini-database in a cell: if a user
  needs a database, they need cards.

### 6.16 Metadata providers

Yes — as **importers**, never render-time dependencies (R9).

```ts
interface MediaProvider {
  id: "openlibrary" | "tmdb" | "musicbrainz" | "igdb";
  search(query: string): Promise<ProviderResult[]>;
  get(externalId: string): Promise<ProviderRecord>;
  mapToFields(record: ProviderRecord): Record<string, unknown>;
  attribution: { text: string; url: string };
  termsUrl: string;
}
```
| Provider | Domain | Key | Notes |
| --- | --- | --- | --- |
| **OpenLibrary** | Books | None | ToS-friendly default |
| **TMDB** | Film / TV | Free key | Attribution required |
| **MusicBrainz + Cover Art Archive** | Music | None | Descriptive `User-Agent` + rate limit |
| **IGDB** | Games | Twitch OAuth | More setup; defer unless games matter |

Store metadata as **card fields plus provenance** (`source`, `externalId`, `fetchedAt`); never fetch
at render (breaks R6, offline, CSP, privacy). **User-owned keys** on the BYOK model (Bet E), never
logged. Rate limits and caching are mandatory; provider outage degrades to "a card without
metadata", never a blocked create. The provider is an importer, not a runtime dependency.

**Covers and artwork are part of the import.** A provider record may include cover or poster URLs
(OpenLibrary Covers, TMDB poster paths, Cover Art Archive). Store the URL and attribution as card
fields and render it through the existing link-image policy (scheme check, `referrerpolicy`, no
provider fetch at render). Uploading a copy remains a user action and uses attachment storage. The
earlier "metadata only, no artwork" posture is dropped: referencing a cover is normal catalogue
behaviour, and the demo needs it.

**Bundled demo metadata.** Starters ship a metadata snapshot (OpenLibrary IDs, titles, authors,
series, publication order, cover URLs) so the Discworld map works with **no API key**. The same
`book`/`source` field schema is used when a user adds a key: the importer refreshes or extends the
snapshot, and the workspace behaves like a canvas-oriented Calibre. A missing key degrades to the
bundled snapshot, not an empty card.

### 6.18 Field-kind integration checklist (14 surfaces)

Every new field kind lands on **all fourteen**, or it ships as a half-feature ◐.

| # | Surface | What must change |
| --- | --- | --- |
| 1 | **Schema** | `fieldKinds` union, `FieldDefinition` options, defaults, migration |
| 2 | **Validation** | `propertyValueError` / `isPropertyValueValid`, readable error |
| 3 | **Display** | `formatProperty` + value reading (empty / unavailable / not-shared / dangling) |
| 4 | **Editing** | `PropertyField` control in panel and library |
| 5 | **Card face** | Compact rendering in `NodeCard`, overflow and truncation |
| 6 | **Views / sort** | Predicate operators and a comparator |
| 7 | **Publish** | Per-kind comparison/conflict in `planPublish` + plan-time validation |
| 8 | **Projection / redaction** | Copy or stub the value and its targets; unshared state (R11) |
| 9 | **Export** | `.suite`, readable JSON, Markdown — all three |
| 10 | **Library / table** | Cell renderer and column behaviour |
| 11 | **Theme selectors** | `prop:` predicate support and a default presentation |
| 12 | **Agent ops** | Plan operation + tool schema + validation |
| 13 | **Stories** | Empty, filled, dangling, unshared, read-only |
| 14 | **Tests** | Unit, property, and a CI `Scenario` (Bet E) |

A "not applicable" must say why. Silently skipping #8 or #9 is how a kind becomes a leak or a
data-loss bug.

**Acceptance:** a `media` card can be created from the Dock, dragged, pasted and published; a PDF
annotation survives a projection share with the right redaction; an excerpt card backlinks and cites;
a chart renders from a view query with an accessible fallback; every new field kind passes the
14-surface checklist; no medium fetches at render time.

## 7. Bet E — Starters and the agent as a first-class client

**Trigger:** E1; E5 if hosted inference is sold. **Depends on:** Bet A (`query_cards`) and the
plan/apply pattern that already exists ✅. **Status:** ○ proposal; no LLM dependency exists today ◐.

### 7.1 Principle

> **Operate the graph, not the UI.**

The agent calls the same typed operations a human uses, through `WorkspaceDocument` — **never raw
Loro** (R2), **never DOM automation**. Graph operations are typed, validated, undoable and fast;
clicks are brittle and unverifiable. **The host holds the credential**: the model sees a workspace
summary and tool results, never the owner key, a share token, or an admin token. The model produces
a plan; the host validates, previews, and applies it.

The recommended form is that starters, CI fixtures, agent output and Copilot actions are
**the same versioned artifact** ○: one implementation, three audiences.

### 7.2 Architecture

```
Copilot / VS Code (MCP tools)
In-app "Compose" panel (app tools)
Admin Lab (admin tools)
        |
        v  same tool surface, different capability token
packages/agent-core
  plan schema | executor | scenario runner | tool definitions | prompts | provider adapter
        |
        v  typed calls only
@suite/graph / WorkspaceDocument -> Loro doc + relay
```

| Component | Responsibility | Must not |
| --- | --- | --- |
| `packages/agent-core` | Plan schema, executor, scenario DSL, tool definitions, prompts, provider adapter | Touch UI, auth, or any network beyond the provider call |
| `apps/agent-mcp` | stdio MCP server for Copilot/VS Code; connects to the dev app + relay with a scoped dev token | Invent its own write path |
| In-app Compose panel | The same tools with the user's session capability | Bypass preview/apply |
| Admin Lab | The same tools + fixtures, scenarios, screenshots, audit | Reuse the unscoped admin token |

The only difference between Copilot and the user is which capability token the host holds and which
surface wraps it ○. There is one implementation and one set of semantics.

### 7.3 `CanvasPlan`

```json
{
  "kind": "suite.canvas-plan", "version": 1, "name": "Product roadmap",
  "requires": { "types": ["Initiative", "Bet"], "fields": ["status", "confidence"] },
  "operations": [
    { "op": "createType", "id": "initiative", "name": "Initiative", "glyph": "◆" },
    { "op": "addField", "typeId": "initiative", "field": {
        "id": "status", "name": "Status", "kind": "select",
        "options": [{ "id": "active", "label": "Active", "order": 0 }] } },
    { "op": "createBoard", "id": "roadmap", "name": "Roadmap" },
    { "op": "createSection", "boardId": "roadmap", "id": "now", "name": "Now" },
    { "op": "createCard", "id": "c1", "typeId": "initiative", "title": "Unify sync",
      "properties": { "status": "active", "confidence": 0.7 }, "tags": ["q4"],
      "placement": { "boardId": "roadmap", "x": 0, "y": 0 } },
    { "op": "createEdge", "id": "e1", "boardId": "roadmap",
      "source": "c1", "target": "c2", "kind": "relates-to", "label": "validates" }
  ]
}
```

- **Versioned operations.** `version: 1` is the contract; unknown ops fail validation; a new op is a
  version bump, never a silent extension. Closed v1 vocabulary: `createType`, `addField`,
  `createBoard`, `createSection`, `createCard`, `createEdge`; later `createView`,
  `createRelationType`, `applyTheme`. No arbitrary calls, no code, no expressions.
- **Preview -> apply -> undo.** Preview reports "3 types, 8 fields, 24 cards, 4 sections, 17 edges"
  before anything is written; apply is one commit; undo restores in one step.
- **Undo scope:** plan apply is a structural undo scope (R14). It never enters a card body's undo
  stack, and a body edit is never undone by reverting a plan.
- **Additive-first.** Create and update by default; **destructive operations require separate
  confirmation**.
- **Validation, not trust.** One Zod schema rejects dangling edges, invalid property kinds, duplicate
  ids, missing boards, and references to unshared content.
- **Determinism.** The executor is deterministic; the LLM is the only nondeterministic part. The same
  plan produces the same document, except for ids of objects the plan does not name.

This is `planPublish`/`applyPublish` ✅: a pure planner plus a replay, applied to workspace
composition.

### 7.8 Providers and key storage

Do not hardcode DeepSeek. One OpenAI-compatible adapter covers the field:

```ts
interface ProviderConfig {
  baseUrl: string;   // https://api.deepseek.com | http://localhost:11434 | https://openrouter.ai/api/v1
  apiKey?: string; model: string; jsonMode: boolean;
}
```
Presets: **DeepSeek** (default), **OpenRouter**, **Ollama**, **LM Studio**, plain OpenAI.
Structured output is required: the model returns a plan, not prose.

| Mode | Key storage | Call path | Pays |
| --- | --- | --- | --- |
| **BYOK standalone/free** | User's local settings, never the server DB | Browser → provider if CORS allows, else a local proxy | User |
| **Hosted BYOK** | User's key in memory, per request; encrypted at rest only if remembered | Browser → `/api/agent/complete` → provider | User |
| **Hosted included** | Server key | Proxy, metered and capped | Operator |
| **Local model** | None | Browser → `http://localhost:11434` (CORS) | User |

The LLM proxy **never needs the workspace credential** ○: the browser applies the plan with the owner
key, keeping write authority in the host. **Free** = BYOK or local model, zero operator inference
cost. **Paid** = a capped allowance per billing period or BYOK, metered on **inference**, never on the
feature (R1) ◐. Cap plan size, turns per generation, and rate per workspace.

### 7.9 Privacy and prompt injection

- **Explicit consent** before sending content; show exactly what will be sent.
- **Schema-only by default**: type/field/tag names, counts, selected titles — **not full bodies**;
  bodies are a per-request opt-in.
- **Never send** owner keys, share tokens, admin tokens, or attachment bytes.
- **Treat card content as untrusted**: delimit it, instruct the model to ignore embedded instructions,
  validate against a closed schema, **reject unknown operations**.
- **A prompt-injection corpus in CI**: "ignore previous instructions", fake system messages,
  tool-call JSON, plans with unknown ops. The executor must still only perform allowlisted operations.
- **Never log prompts or bodies** in a hosted proxy by default; log token counts and error classes.

### 7.10 Live integrated testing

- **Schema stress:** one card per field kind; boundary values; a plan with valid and invalid writes;
  assert the valid ones succeed, the invalid ones throw the expected error, and no partial state
  remains; screenshot the board; check theme contrast.
- **Constraint fuzzing with `fast-check`:** generate plans, apply to a throwaway workspace, assert no
  dangling edges, orphan placements, duplicate ids, invalid values, out-of-schema writes, and that
  undo restores the prior snapshot.
- **Hypothesis records:** statement, assumptions, scenario, metric, threshold, result. The Lab runs
  the scenario, captures evidence, records the observation.
- **Dogfood:** a *Research* workspace where hypotheses and evidence are cards and `supports`/
  `contradicts` are edges. The research log becomes a canvas, which also tests the product against
  its own model ○.
- The LLM proposes realistic scenarios; the fuzzer finds the nasty ones. Use both.

Phase 1 is a testing-infrastructure investment, not an agent feature. It can start before E1 and E5
because it is limited to the plan format, executor, starters, and CI scenarios. Phases 2–4 remain
gated by E1 and, where hosted inference is sold, E5.

### 7.12 Avoid list

DOM automation as the primary path (graph tools only; Playwright for visual checks) · the LLM holding
the owner key · auto-applying plans · sending full bodies by default · a generic "chat with your
notes" · a starter marketplace before the plan format is stable · hardcoding DeepSeek · shipping
Discworld as a commercial marketing asset without IP care · **making the agent a dependency for core
functionality** — the app must remain fully usable with no LLM, no key, no network (R6).

### 7.13 Summary statement

> Starters, scenarios, and agent output are the same `CanvasPlan`. The demo is the test. The agent is
> another client. Copilot and the user run the same tools. The model produces a plan; the host
> applies it. ○

**Acceptance:** each starter runs as a CI scenario from clean state; a plan is previewed, applied and
undone in one step; an invalid plan writes nothing; the injection corpus cannot cause a
non-allowlisted operation; Copilot and the in-app panel produce identical documents from one plan;
and the app still works with the provider removed.

## 8. Bet F — Scale and the data plane

**Trigger:** E2 and E6 — **a measured ceiling**, not a predicted one.
**Status:** ○ proposal. Some facts are ✅ verified from the audit pass.

### 8.1 Two planes, one engine

| Plane | Contents | V1 default | V2 candidate |
| --- | --- | --- | --- |
| **Control plane** | users, sessions, workspaces, owner hashes, shares, licences, limits, usage, audit, jobs | Postgres arrives **with Better Auth in V1** ○ (shared convention) | Same; more tables, more tenants, region pinning |
| **Document plane** | Loro snapshots, share projections | SQLite BLOB per room ✅ (`documents(name, state BLOB, updated_at)` ◐) | Postgres BLOB, then object storage — **only if measured** |

The important sentence from the audit, kept verbatim because it is the whole section:

> **Postgres is the right answer to "who are you, what may you open, and what did you use" — it is
> the wrong answer to "why is this board slow."** ◐

Postgres does not fix event-loop-blocking saves, write amplification, room memory residency,
projection fan-out, or presence. It makes auth, entitlements, quotas, audit, usage metering,
advisory locks, and multi-replica coordination possible.

### 8.2 What V2 actually changes (T2 / T3)

| Tier | Adds | Trigger | Acceptance |
| --- | --- | --- | --- |
| **T2 — heavy rooms** | A **worker process** for saves and projections; documents in Postgres or object storage **if measured**; incremental updates + periodic compaction | p95 save latency or event-loop lag breaches the budget; projection rebuild cost grows with share count | Save latency back inside budget under the load test; projections no longer block the relay |
| **T3 — multi-replica** | **Redis** for presence and rate limits; **room leases** via Postgres advisory locks; sticky routing; cross-process events | One process cannot hold the rooms, or availability requires a second replica | Two replicas serve the same workspace with no split-brain; lease takeover is tested |
| **Object storage** | Attachments and media bytes with signed reads (the seam `attachments.ts` already declares ✅) | Attachment bytes threaten the DB, or media lands (Bet D) | Signed read, range requests, quota accounting, deletion |
| **Index/card split** | Index document + per-card documents | The index leaves the "small, hot" profile, or one body dominates open time (design doc's own signals ✅) | Board open scales with what is viewed, not with the workspace |

Ordering inside V2 is dependency-driven: **save path → projections → presence → leases → multi-
replica**, because each one changes what the previous one has to be correct about.

### 8.3 Comparison with Logseq

Logseq's pain came from a specific design, not from "no Postgres" ◐:

- A **file per page**, re-parsed and re-indexed from Markdown.
- **Per-block references** in a flat tree, so backlinks and queries fan out over large in-memory
  structures.
- **External sync tools** (iCloud/Dropbox/Git) producing conflicting copies.
- **Full-graph queries in memory**, with slow cold starts.

Suite avoids the first and third by construction (one CRDT document per workspace, no file tree, no
OS-level sync ✅). It inherits the second and fourth in a different form: the document grows with
every body, and the whole thing loads into memory per room, with `SUITE_PROJECTION_ROOMS_MAX`
defaulting to 128 ◐.

So the risk is not "Logseq's bug will happen here". It is that **Suite hits the same ceiling from the
other side**: Logseq was slow because it re-parsed files; Suite is slow because it serializes and
holds whole documents. The mitigation is the same shape in both cases ○:

> **Don't make the unit of loading equal to the unit of thinking.**

That is the index/card split, and it is the eventual answer — not Postgres.

### 8.4 "Promotion" is an adapter swap, never a fork

Do not ship two architectures (R1). Storage is a substrate behind interfaces that already exist ◐:

- `DocumentStore` — `load`, `save`, `delete`, `close`
- `DocumentInventory` — `list`, `size`, `inventory`
- `DocumentMaintenance` — `optimize`, `startMaintenance`, `journalMode`
- `ShareStore`, `WorkspaceRegistry`, `SettingsStore`

```
createDocumentStore(path) -> SQLiteDocumentStore    (self-host, single box, embedded)
                          -> PostgresDocumentStore  (hosted, multi-replica)
                          -> ObjectStoreDocuments   (large workspaces: object storage + metadata row)
```
Because document state is opaque bytes keyed by name, migrating a workspace between substrates is a
`SELECT` → `INSERT` copy — no schema mapping, no dual write, no backfill ✅. This is the main
benefit of the opaque-blob design; decomposing documents into rows would remove it.

Add one thing before it is needed: a **format tag** on the blob (`loro-snapshot-v1`) so a future
substrate can refuse or convert an unknown format instead of importing malformed data ○.

**Conformance is a precondition, not follow-up work.** One adapter test suite runs the same
assertions against `DocumentStore`/`ShareStore`/`WorkspaceRegistry`; no storage adapter ships —
including the first Postgres one — unless it passes against the existing in-memory and SQLite
implementations. Only then is "promotion" a configuration value with evidence behind it, rather than
a second code path with an untested contract.

### 8.5 What paid users actually buy

| Sold | Not sold |
| --- | --- |
| Larger workspace / document / attachment quotas ✅ (the knobs exist) | "Your data is in a real database" |
| Longer retention, more backups, faster restore | A different engine or a feature fork |
| Region selection (second Postgres + relay) | Priority *semantics* — priority is a queue, not a code path |
| Priority on heavy operations | Exclusivity of product features that self-hosters lack |
| Audit export, SSO, admin roles (later) | A "large workspace" build |

A "large workspace" tier is an **operational** tier: bigger instances, object storage, a dedicated
projection worker. Same code, different limits and topology (R1).

### 8.6 Meter what will be billed

Usage rows from the first release, in the control plane: document bytes, attachment bytes, active shares,
projection CPU, agent inference (Bet E). Pricing requires usage measurement ◐, and a quota that
cannot be enforced is not a real limit.

## 9. Bet G — Platform and reach

**Trigger:** E1 by segment, E6 for the ones that generate support load.
**Status:** ○ proposal. Each item lists what must be true **before** it starts.

| Initiative | Why it matters | Preconditions (all must hold) | First slice |
| --- | --- | --- | --- |
| **i18n** | Non-English users are a large share of PKM demand ○ | Strings externalized with a lint that fails on new hardcoded copy; locale-aware dates/numbers; RTL layout pass; translated docs for the top two locales | UI shell + canvas chrome; card content untouched |
| **Mobile / touch** | Reading and light capture happen on phones ○ | Pointer-events abstraction (no hover-only affordances); touch targets; gesture conflicts resolved (pan vs. select vs. drag); performance budget on a mid-range phone | Read + inspect + light edit on a board; not full authoring |
| **E2EE** | High value, high complexity | **After accounts** (E2EE needs identity); key recovery design; share capability semantics under E2EE; search/index implications; backup consequences | Workspace document encryption with device-held keys; document the recovery trade-off |
| **Importers** | Switching cost is the main adoption barrier ○ | Mapping wizard (same machinery as theme binding §5.4); lossy-import report; idempotent re-import; no partial writes | Markdown folder → cards; then Notion; then Heptabase |
| **Comments / threads** | Collaboration needs discussion that is not content | Identity for authorship (accounts); retention policy; projection redaction rules; notification decision | Card-anchored threads, board-scoped |
| **Version history / time travel** | Users need to inspect prior states | Storage for historical snapshots separate from live state; per-scope restore (card vs. workspace); conflict-aware restore; quota impact | Per-card history from existing update logs, read-only restore |
| **Full accessibility audit** | Required; also exposes design debt | Keyboard map complete; focus order on canvas; screen-reader support for a spatial surface (list/outline alternative); contrast gates in CI; reduced-motion support | WCAG 2.2 AA audit + a published conformance statement with known gaps |

Constraints that apply to each item:

- **i18n requires string extraction first.** Retrofitting is more costly because copy is embedded in
  components.
- **Mobile requires an input-model change, not only a layout change.** Shrinking a hover-dependent
  canvas does not make it touch-friendly.
- **E2EE forecloses some features.** Server-side search, server-side projections, and support
  "look at your workspace" all change. Decide what is lost *before* promising it.
- **Importers have the widest effect at the lowest cost.** They convert curiosity into retained
  workspaces and reuse the binding machinery Bet C needs.
- **Comments before notifications.** Comments without notifications are unlikely to be used.
  Notifications need identity, so the order is accounts → comments → notifications.
- **Version history is primarily a storage decision.** Define metering before promising unlimited
  history.

## 10. Cross-cutting feature tax

Every feature in V2 pays the same tax. This is the mechanism that prevents a pile of
half-integrated node kinds and record types ◐.

| Tax | Applies to | Evidence required |
| --- | --- | --- |
| **1. A `CanvasPlan` / starter / transformer** | Every feature that creates structure | A plan file that builds the feature's example state from blank |
| **2. A CI `Scenario`** | Every feature | Setup + actions + assertions, run on every commit |
| **3. A publish-allowlist entry** | Every new rich-text node or reference kind | `RICH_TEXT_NODE_ATTRIBUTE_NAMES` ✅ + `publishValidation.ts` ✅ |
| **4. A projection test** | Every new record type or field kind | Copy / redact / drop behaviour asserted for board, card, and selection shares ✅ (ADR-0022/0023) |
| **5. The 14-surface field-kind checklist** | Every new field kind | §6.18, all fourteen items or a written "not applicable" |
| **6. Editor schema contract** | Every new node kind | `editorSchemaContract.test.ts` ✅ passes; the allowlist and editor schema do not drift |
| **7. Export coverage** | Every new record or kind | `.suite`, readable JSON, Markdown |
| **8. Undo scope declaration** | Every new structural write | Named scope (structural vs. text) per R14 |
| **9. Theme selector support** (once Bet C ships) | Every new predicate-able kind | `prop:`/`rel:` behaviour or an explicit "not styleable" |
| **10. Query support** (once Bet A ships) | Every new value or relationship | The evaluator's property/has predicates behave correctly |

**Enforcement.** A feature that has not completed items 1–4 does not merge to the default branch; it
stays behind a flag per R8. Items 5–10 are required before the feature is announced, not before the
flag is enabled.

### The node-kind guardrail

> **Every new rich-text node kind must be added to `RICH_TEXT_NODE_ATTRIBUTE_NAMES` ✅, to
> `publishValidation.ts` ✅, and to the editor schema contract ✅ — or publishing rejects it and the
> contract test fails.**

This guardrail prevents a share link from being broken by a node the publisher does not understand.
The failure mode is a card that publishes blank.

### The "no new object class" checklist

Before adding any record type, answer:

1. Can this be a **card type** (R7)? If yes, stop.
2. Can it be a **derived view** over existing records (R12)? If yes, stop.
3. Does it need **record-granular writes** that a card property cannot express (annotations, relations)?
4. Does it need a **different projection/redaction unit** than a card?
5. Does it need to **exist without any card** (annotations on a source, relations between cards)?

Only a "yes" to 3, 4, or 5 justifies a root. Relations and annotations pass; themes pass (workspace
configuration, not per-card data); media does not (it is a card).

## 12. Dependency-ordered sequence

Three phases. A phase starts when its entry gate opens and its predecessors are done.

### Phase V2-A — v1.1 media and retrieval

**Entry:** E1 + E7 + E8 open. **Exit:** a stranger can start from a starter, add media, query it,
present it, and share it.

1. **Bet A — Views v2**: query object, predicates, grouping, presentation; one engine wired to the
   library, board filters, saved views, and `query_cards`. *(Precondition for B, C, E and charts.)*
2. **Bet D — media**: attachments → media (object-store seam, MIME matrix, caps); Add Media in the
   Dock with drag/paste routing; built-in `source`/`media` card type.
3. **Bet D — scenes**: scenes root + presentation mode (reuses `focusTarget`). Lowest-cost high-value
   item here.
4. **Bet D — chat**: board-scoped chat room + projection redaction. Included only because transport
   is free and board scoping contains its risk.

### Phase V2-B — sources become first-class

**Entry:** V2-A exit + E4 (share usage) + E2 (storage headroom). **Exit:** the extraction pipeline
works end to end, themes render meaning, and the agent can build and test.

1. **Bet D — annotations**: root + polymorphic anchors + PDF + excerpt promotion.
2. **Bet D — `attachment` field kind**, through the 14-surface checklist (§6.18).
3. **Bet D — metadata providers** as importers (BYOK).
4. **Bet B — relation types**: `relationTypes` + `relationTypeId` + the `relation` field kind (a
   view, never a store). Requires Bet A predicates and a new ADR superseding ADR-0019's half.
5. **Bet C — constrained themes**: tokens → selectors → rules → instance. Requires Bet A selectors;
   `rel:` only after Bet B.
6. **Bet D — charts**, auto-arrange command + collection cards.
7. **Bet E — plans/executor/starters** (Phases 1–2), then providers (Phase 3).

### Phase V2-C — heavy media and reach

**Entry:** V2-B exit + E8 (validated demand) + E2/E6 (storage economics). **Exit:** reach beyond the
desktop power user without forking the architecture.

1. **Bet D**: video link-first → uploads (only if link-first is used); EPUB with text-quote
   anchoring; table field (only after table view, with a cell-CRDT ADR).
2. **Bet F**: T2 worker → T3 leases/Redis → object storage → index/card split **if measured**.
3. **Bet G**: importers, i18n, mobile, comments, version history, a11y, E2EE.

### Cross-phase rules

- **Nothing in V2 starts while a V1 gate is failing.** V2 is expansion; V1 is the promise. If the
  save path stalls or restore is untested, V2 work takes capacity from V1.
- **A bet may be reordered only when a gate changes state.** Record which gate changed.
- **Phase exits are evidence.** Each exit statement is a claim someone can check.
- **The sequence is a dependency graph, not a queue.** Items inside a phase may run in parallel on
  disjoint surfaces — but B and C both depend on A, and D's media work blocks its annotations.

| **D10** | Which media types are allowed at upload? | Closed list, growing per medium, all published in the allowlist ✅ | Images → PDF → audio/video link-first | A security review finding, or storage economics |
| **D11** | Does the agent see card bodies? | Schema-only default, bodies on explicit consent (recommended) | Schema-only | Users repeatedly ask for body-aware generation **and** a privacy review passes |
| **D12** | Do themes bind by name or by role? | Name-based binding + wizard (recommended) vs. `role:` on types | Name-based | Portable themes become a real distribution channel |

### Review input: narrow V2

An external operator review proposes cutting V2 to **importers, starters, scenes, table view, and one
of (annotations, themes, typed links)**, and deferring themes-as-a-studio, chat, charts, the agent, and
heavy media until user demand exists. This is not a decision. It is the main scope question for the
next planning phase, and it reflects a real risk: the current list describes a different product from
the one shipping today. If accepted, the cut bets move to a "deferred indefinitely" list rather than a
"maybe."

### Pinned for discussion: is a board just a view?

A Beta observation (see [beta.md](./beta.md) §4.12) suggests closing a board tab should *file the
board into Views* rather than send it to the library. If that is right, a board and a saved view are
two presentations of one idea: a saved view picks cards by predicate, a board places them spatially.
That reading would give Bet A a second job — Views becomes the container for boards, saved queries,
and later scenes — and it would answer `D7` earlier than planned.

It also raises questions this document cannot answer yet:

- Does a board carry a query (a filtered spatial view), or only placements?
- If Views holds boards, is the tab strip a *selection* of Views rather than the board list itself?
- Does closing a board become a per-user or a workspace fact? A per-user close is simpler and keeps
  another client's tab alive, but then "views" differ per person, which contradicts `R12`.
- Do portal cards keep working for a filed board? They must, or filing would break A11.

Nothing here changes a decision in §14 yet. It is recorded so the `D7` choice is made once, with
this framing on the table, rather than twice.

### Open questions (not decisions yet)

1. **Does a board share carry annotations on cards it does not include?** Leaning: no (§14 D5), but
   the boundary is a filter over a root, so the cost of "yes" is low and the risk is not zero ◐.
2. **Can a theme reference a relation type that does not exist yet?** Leaning: yes, as an unbound
   requirement in the wizard, inert until bound (§5.4).
3. **Does an excerpt card own its quote, or reference the annotation forever?** Leaning: copy on
   promotion, keep the annotation id for provenance — one-way, idempotent (§6.5).
4. **Should `query_cards` be able to return bodies?** Leaning: no; summaries plus `get_card` per id
   (privacy, token budget) ○.
5. **How is the Discworld preset shipped?** Leaning: bundled starter with an OpenLibrary metadata
   snapshot and link-image covers, importable and non-mutating (§7.7) ○.
6. **What is the retention policy for annotations when a source is deleted?** Leaning: annotations
   become orphaned and read-only, promotable but not re-anchorable.
7. **Do projections rebuild on theme change?** Leaning: yes, debounced per workspace, because a
   shared board that looks different is a correctness bug in the share (§5.7).
8. **Which comes first, importers or i18n?** Leaning: importers — they convert curiosity into
   retained workspaces, and they reuse the binding wizard (§9).

## Summary

V2 is the part of this roadmap furthest from evidence, so every bet opens with a trigger and every
claim carries a marker.

The constraints that take precedence over any bet:

- **Cards are objects, boards are contexts, projections are derived views.** ✅ ADR-0020, design doc §1.
- **Derived stays derived; stored stays minimal.** ✅ R12.
- **One architecture, one query engine, one annotation model, one plan format.** ○ R1–R4.

When a bet conflicts with one of these, the bet is changed or cut.
